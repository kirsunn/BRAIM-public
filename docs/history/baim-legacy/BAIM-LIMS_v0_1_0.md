# BAIM-LIMS — Стандарт жизненного цикла, зрелости и состояния информационных моделей

**Полное название:** BAIM Lifecycle, Information Maturity & State Standard  
**Русское название:** Стандарт BAIM жизненного цикла, зрелости и состояния информационных моделей  
**Идентификатор:** `BAIM-LIMS`  
**Версия:** `0.1.0`  
**Статус:** Draft / рабочая концептуальная спецификация  
**Дата:** 2026-09-30  

---

## 1. Назначение

BAIM-LIMS устанавливает единую систему описания:

1. жизненного цикла здания, сооружения или другого актива;
2. контекста информационной модели (`PIM` или `AIM`);
3. фазы, стадии, этапа и подэтапа жизненного цикла;
4. типа информационной модели;
5. состояния информационной модели в среде общих данных (СОД / CDE);
6. версии, выпуска и архивной истории;
7. цифровой зрелости и готовности информации по профилю `MICMTR`;
8. допустимости конкретной операции: расчёта, координации, выпуска документации, передачи в экспертизу, строительства, эксплуатации или сноса.

Стандарт предназначен для BAIM Core, аналитической модели здания, коннекторов к BIM-платформам, IFC/IDS-валидации, СОД, CDE, а также для подготовки моделей к передаче между участниками жизненного цикла.

BAIM-LIMS не заменяет IFC, IDS, ISO 19650, требования заказчика, нормативные документы или BIM Execution Plan. Он связывает их в машиночитаемую систему правил BAIM.

## 2. Основной принцип

В BAIM-LIMS разделяются четыре разных, но связанных измерения:

| Измерение | Вопрос | Пример |
|---|---|---|
| Жизненный цикл актива | Где находится объект в жизненном цикле? | `PIM-P-PP-EX` |
| Жизненный цикл ИМ / CDE | В каком состоянии находится конкретная модель? | `WIP`, `SHR`, `PUB`, `ARC` |
| Зрелость информации | Насколько модель готова? | `M2-I2-C111-M4444-T4-R444` |
| Операция | Что разрешается сделать с моделью? | `documentation.release` |

Каноническая цепочка принятия решения:

```text
ЖЦ ЗиС / актива
→ PIM или AIM
→ фаза / стадия / этап / подэтап
→ тип ИМ
→ состояние ИМ в СОД
→ Required MICMTR
→ Actual MICMTR
→ IDS / IFC / внутренние проверки
→ разрешить / вернуть в работу / опубликовать / архивировать
```

**Правило:** жизненный цикл, состояние СОД и зрелость — не взаимозаменяемые показатели.

- Код ЖЦ отвечает на вопрос: **где находится объект и процесс**.
- Состояние ИМ отвечает на вопрос: **можно ли использовать эту версию информации и для чего**.
- MICMTR отвечает на вопрос: **достаточны ли геометрия, данные, соответствие, точность и связи для операции**.

## 3. Термины и сокращения

| Термин | Определение |

## 4. Контейнеры информации: PIM и AIM

| Код | Термин | Назначение |
|---|---|---|
| `PIM` | Project Information Model | Информация для концепции, изысканий, проектирования, экспертизы, закупки, создания и ввода объекта |
| `AIM` | Asset Information Model | Информация для использования, эксплуатации, обслуживания, ремонтов, реконструкции, вывода из эксплуатации и утилизации |

### 4.1. Переход PIM → AIM

Переход из `PIM` в `AIM` происходит не автоматически и не только по дате ввода объекта. Он требует:

1. формирования исполнительной / as-built информации;
2. проверки фактических геометрии, данных и связей;
3. достижения требуемого профиля зрелости;
4. публикации и утверждения опорной ИМ;
5. передачи утверждённой информации эксплуатирующей стороне.

Базовый контрольный контекст перехода:

```text
Lifecycle: PIM-S-IE
CDE state: PUB
Model type: RIM
Required profile: M8-I8-C222-M8888-T8-R888
Operation: handover.pim_to_aim
```

### 4.2. Реконструкция как новая итерация

Реконструкция не является окончательной линейной точкой ЖЦ. Она использует данные AIM как исходные и запускает новую проектную итерацию.

```text
AIM-U-REK
→ PIM-C-K / PIM-P-PP / PIM-P-PR / PIM-S-CON
→ обновлённый AIM
```

При этом исходные атрибуты, история обслуживания, фактические параметры и документы актива наследуются как входные данные новой итерации.

## 5. Классификатор жизненного цикла

### 5.1. Формат кода

Код ЖЦ имеет формат:

```text
{CONTAINER}-{PHASE}-{STAGE}[-{STEP}[-{SUBSTEP}]]
```

где:

- `CONTAINER` — `PIM` или `AIM`;
- `PHASE` — укрупнённая фаза ЖЦ;
- `STAGE` — стадия;
- `STEP` — этап;
- `SUBSTEP` — подэтап, если требуется.

Примеры:

```text
PIM-C-K
PIM-C-KOBIN-COST
PIM-P-PP-EX
PIM-P-PR-PERM
PIM-S-CON-ZC-EW
PIM-S-IE-PNR
AIM-U-OPS-TR
AIM-U-REK-PRJ
AIM-D-DEM-PRJ
```

### 5.2. Фазы ЖЦ

| Код | Русское название | Английское название | Контейнер |
|---|---|---|---|
| `C` | Концепция | Concept | `PIM` |
| `P` | Проектирование | Design | `PIM` |
| `S` | Создание | Creation / Construction | `PIM` |
| `U` | Использование | Use / Operation | `AIM` |
| `D` | Утилизация / вывод из эксплуатации | Decommissioning / Disposal | `AIM` |

| Код | Фаза | Стадия | Этап | Подэтап / пояснение |

### 5.4. Принцип иерархии

Стадия в конкретном проекте может быть этапом или подэтапом другой стадии. BAIM-LIMS допускает расширение дерева ЖЦ для отраслевых особенностей: атомная энергетика, линейная инфраструктура, РЖД, дороги, промышленные объекты и другие типы проектов.

Новый код не должен менять смысл существующего кода. Новые ветви добавляются как расширения классификатора.

## 6. Типы информационных моделей

| Код | Тип модели | Назначение |
|---|---|---|
| `DIM` | Дисциплинарная ИМ | Результат работы конкретной дисциплины, раздела, марки, тома или специалиста |
| `FIM` | Общая / объединённая / федеративная ИМ | Координированная ИМ объекта, объединяющая дисциплинарные данные |
| `RIM` | Опорная ИМ | Зафиксированный и публикуемый результат стадии, этапа или процесса; вход для следующей стадии |
| `CIM` | Сводная ИМ | Виртуальное объединение ссылок в СОД для анализа и координации; не должно изменять источники |
| `ANM` | Аналитическая ИМ | ИМ, содержащая расчётные данные, нагрузки, результаты расчётов или аналитические показатели |
| `PRM` | Параметрическая модель | Модель с управляемыми атрибутами, зависимостями, правилами и ограничениями |

### 6.1. Принцип ответственности

Дисциплинарная ИМ принадлежит создавшей её ответственной стороне. Другие участники могут использовать опубликованную или общедоступную версию как ссылку, но не должны изменять её содержимое напрямую.

### 6.2. Опорная ИМ

Ключевой переход между стадиями должен сопровождаться выпуском `RIM`:

```text
тип модели: RIM
состояние СОД: PUB
статус проверки: verified
назначение: входные данные следующей стадии / этапа
```

## 7. Жизненный цикл ИМ и состояния СОД

### 7.1. Канонические состояния

| Код | Состояние | Назначение | Допустимое использование |
|---|---|---|---|
| `WIP` | В работе | Разработка информации автором или группой выполнения задачи | Только внутри ответственной группы |
| `REV` | На проверке / согласовании | Проверка, рассмотрение, координация, утверждение | Использование для проверки; не для целевой поставки |
| `SHR` | Общий доступ | Совместное использование принятых промежуточных решений | Чтение, координация, ссылки; без изменения источника |
| `PUB` | Опубликовано | Разрешённая, принятая, подписанная или выданная информация | Применение строго по назначению выпуска |
| `ARC` | Архив | Неизменяемая история выпусков, состояний и транзакций | Только чтение, доказательная и историческая запись |

### 7.2. Разрешённые переходы

```text
WIP → REV → SHR → PUB → ARC
```

Допускаются возвраты в `WIP`, если модель не прошла проверку, координацию или утверждение:

```text
REV → WIP
SHR → WIP
PUB → WIP (только через новый выпуск / изменение; опубликованная версия остаётся в ARC)
```

### 7.3. Обязательные метаданные ИМ

Каждая управляемая ИМ должна содержать как минимум:

```text
- lifecycle_code
- model_type
- cde_state
- release
- revision
- authoring_party
- responsible_party
- intended_use
- required_profile
- actual_profile
- validation_status
- created_at
- updated_at
```

### 7.4. Версия и выпуск

BAIM-LIMS различает:

- **выпуск (`release`)** — зафиксированная поставка или изменение, предназначенное для обмена;
- **версия (`revision`)** — итерация внутри работы над выпуском;
- **состояние (`cde_state`)** — пригодность модели к использованию;
- **архивная запись** — неизменяемая история предыдущего выпуска или версии.

Формат именования файлов и детальная политика нумерации выпусков выносятся в отдельное приложение `CDE Naming and Revision Policy`.

## 8. Профиль зрелости MICMTR

### 8.1. Каноническая запись

```text
M-I-C-M-T-R
```

Полная форма:

```text
M{m}-I{i}-C{c1}{c2}{c3}-M{r}{f}{l}{o}-T{t}-R{g}{l}{i}
```

Пример:

```text
M2-I2-C111-M4444-T4-R444
```

| Позиция | Регистр | Значение |
|---|---|---|
| 1 | `M` — Model | Уровень геометрического представления |
| 2 | `I` — Information | Уровень информационного наполнения |
| 3 | `C` — Conformance | Соответствие: геометрия → логика → информация |
| 4 | `M` — Geometric Maturity | Размер → форма → местоположение → ориентация |
| 5 | `T` — Tolerance | Геометрический допуск / точность |
| 6 | `R` — Relationships | Геометрические → логические → информационные связи |

### 8.2. Правило значений

Для регистров `M`, `I`, второго `M`, `T` и `R` используются только чётные уровни:

```text
0, 2, 4, 6, 8, 10
```

Нечётные значения `1, 3, 5, 7, 9` зарезервированы для будущих промежуточных уровней и не используются в версии `0.1.0`.

Исключение: каждая ось `C` имеет значения `0`, `1`, `2`:

| Значение | Смысл |
|---:|---|
| `0` | Соответствие не задано или не проверялось |
| `1` | Соответствие проекту / внутренняя согласованность |
| `2` | Соответствие факту или внешним подтверждённым данным |

### 8.3. M — Model

| Код | Уровень |
|---|---|
| `M0` | Символ или отсутствие объёмного представления |
| `M2` | Условный объём объекта, системы или сборки |
| `M4` | Объём с разделением по материалам или основным слоям |
| `M6` | Конструктивное представление с рабочими размерами и составом |
| `M8` | Полное графическое представление изделия или элемента |
| `M10` | Фактическая геометрия, обследование, облако точек или подтверждённое as-built состояние |

### 8.4. I — Information

| Код | Уровень |
|---|---|
| `I0` | Концептуальная информация: назначение, ТЭП, допущения |
| `I2` | Данные для проектной документации |
| `I4` | Данные для рабочей документации и строительства |
| `I6` | Деталировочные данные для изготовления или монтажа |
| `I8` | Фактические технические и геометрические данные as-built |
| `I10` | Данные для эксплуатации, обслуживания, ремонтов и управления активом |

### 8.5. C — Conformance

```text
C = [C-M][C-L][C-I]
```

| Позиция | Ось |
|---|---|
| Первая цифра | Геометрическое соответствие |
| Вторая цифра | Логическое соответствие |
| Третья цифра | Информационное соответствие |

Примеры:

```text
C000 — соответствие не проверено
C100 — проверена геометрия на проектном уровне
C010 — проверена логика на проектном уровне
C001 — проверена информация на проектном уровне
C111 — геометрия, логика и информация соответствуют проектной модели
C222 — геометрия, логика и информация подтверждены относительно факта / внешних данных
```

Все 27 комбинаций `C` допустимы на уровне записи. Для конкретной операции валидность определяется её Required Profile и правилами валидации.

### 8.6. Второй M — Geometric Maturity

```text
M = R-F-L-O
```

| Позиция | Значение |
|---|---|
| 1 | Размер / Size |
| 2 | Форма / Form |
| 3 | Местоположение / Location |
| 4 | Ориентация / Orientation |

Уровни: `0`, `2`, `4`, `6`, `8`, `10` — от не задано до подтверждённого фактического состояния.

Пример:

```text
M6426
R6 — проектный размер
F4 — приблизительная форма
L2 — условное местоположение
O6 — проектная ориентация
```

### 8.7. T — Tolerance

| Код | Допуск |
|---|---|
| `T0` | Не задан |
| `T2` | До ±100 мм |
| `T4` | До ±50 мм |
| `T6` | До ±10 мм |
| `T8` | До ±5 мм |
| `T10` | Специально установленная / фактически подтверждённая точность |

Конкретное численное значение допуска хранится отдельным атрибутом с единицей измерения.

### 8.8. R — Relationships

```text
R = G-L-I
```

| Позиция | Тип связи |
|---|---|
| 1 | Геометрические связи |
| 2 | Логические связи |
| 3 | Информационные связи |

| Уровень | Значение |
|---:|---|
| `0` | Связь отсутствует |
| `2` | Связь заявлена |
| `4` | Ссылочная связь существует |
| `6` | Связь определена внутри проекта |
| `8` | Связь согласована с внешними данными |
| `10` | Связь подтверждена фактом или проверенной системой |

### 8.9. Без агрегирования

BAIM-LIMS не вводит агрегированный индекс зрелости. Профиль сравнивается по отдельным регистрам и позициям. Агрегаты наподобие `min()` могут применяться локально в аналитике, но не являются каноническим кодом, полем или критерием стандарта.

## 9. Required / Actual Profile и статусы проверки

Для каждого элемента, ИМ, набора данных или операции хранятся отдельно требуемый и фактический профили.

```json
{
  "required_profile": "M2-I2-C111-M4444-T4-R444",
  "actual_profile": "M2-I2-C110-M4444-T4-R444",
  "validation_status": "recheck_required"
}
```

### 9.1. Статусы

| Статус | Значение |
|---|---|
| `unknown` | Профиль неизвестен |
| `assumed` | Принят как допущение |
| `proposed` | Предложен системой или автором |
| `in_progress` | Находится в работе |
| `complete` | Данные собраны, но ещё не подтверждены |
| `verified` | Профиль и требования подтверждены |
| `outdated` | Профиль устарел после изменения |
| `recheck_required` | Нужна повторная проверка |
| `rejected` | Требования не выполнены |

### 9.2. Правило сравнения

Операция допускается, если:

1. `actual_profile` достигает `required_profile` по каждому соответствующему регистру и каждой позиции;
2. `validation_status` допускает применение модели;
3. состояние СОД соответствует назначению операции;
4. модель имеет требуемый тип (`DIM`, `FIM`, `RIM`, `CIM`, `ANM`, `PRM`);
5. обязательные IFC/IDS и внутренние правила проверки пройдены.

## 10. Операционные ворота

### 10.1. Принцип

Каждая операция должна иметь:

```text
- lifecycle_scope
- allowed_model_types
- minimum_cde_state
- required_micmtr_profile
- required_ids_rules
- decision_on_failure
```

`C` выступает как предохранитель операций: если требуемое геометрическое, логическое или информационное соответствие не достигнуто, операция блокируется либо переводится в режим предупреждения — в зависимости от политики проекта.

### 10.2. Стартовая матрица

| Контекст ЖЦ | Тип ИМ | Мин. состояние СОД | Мин. MICMTR | Операция |
|---|---|---|---|---|
| `PIM-C-K` | `PRM`, `DIM` | `WIP` | `M0-I0-C000-M0000-T0-R000` | Формирование концепции |
| `PIM-C-KP` | `PRM`, `ANM`, `DIM` | `SHR` | `M2-I0-C010-M2222-T2-R222` | Вариантное проектирование, первичные расчёты |
| `PIM-P-PP` | `DIM`, `FIM` | `REV` | `M2-I2-C111-M4444-T4-R444` | Комплексная проверка и подготовка ПД |
| `PIM-P-PP-EX` | `RIM` | `PUB` | `M2-I2-C111-M4444-T4-R444` | Передача на экспертизу |
| `PIM-P-PR` | `DIM`, `FIM` | `SHR` | `M4-I4-C111-M6666-T6-R666` | Координация и выпуск РД |
| `PIM-S-TND-FAB` | `RIM`, `FIM` | `PUB` | `M6-I6-C111-M6666-T6-R666` | Изготовление и закупка |
| `PIM-S-CON` | `RIM`, `FIM` | `PUB` | `M6-I6-C111-M6666-T6-R666` | Строительство |
| `PIM-S-IE-PNR` | `RIM`, `ANM` | `PUB` | `M8-I8-C222-M8888-T8-R888` | ПНР, приёмка и подготовка передачи |
| `PIM-S-IE` | `RIM` | `PUB` | `M8-I8-C222-M8888-T8-R888` | Передача PIM в AIM |
| `AIM-U-OPS` | `FIM`, `RIM` | `PUB` | `M8-I10-C222-M8888-T8-R888` | Эксплуатация и обслуживание |
| `AIM-U-REK-PRJ` | `PRM`, `ANM`, `DIM` | `WIP` | Определяется заданием | Запуск нового проектного цикла реконструкции |
| `AIM-D-DEM-PRJ` | `DIM`, `ANM`, `RIM` | `PUB` | Определяется проектом сноса | Подготовка проекта сноса |

Профили в этой матрице являются стартовыми и подлежат проверке на реальных объектах, типах элементов и дисциплинах.

## 11. Связь с IFC, IDS и BIM-платформами

### 11.1. Независимость от платформы

BAIM-LIMS не привязан к конкретному авторскому ПО. Renga, Revit, Archicad и другие BIM-платформы используются через сменные коннекторы.

Канонические данные BAIM-LIMS должны быть платформонезависимыми и передаваться через:

- IFC-сущности и отношения;
- пользовательские свойства и property sets;
- IDS-спецификации;
- API-коннекторы;
- собственную аналитическую модель BAIM.

### 11.2. Минимальный набор свойств

Для элемента или модели рекомендуется определить набор `Pset_BAIM_LIMS`:

```text
BAIM_LifecycleCode
BAIM_ModelType
BAIM_CDEState
BAIM_Release
BAIM_Revision
BAIM_RequiredProfile
BAIM_ActualProfile
BAIM_ValidationStatus
BAIM_IntendedUse
BAIM_ResponsibleParty
```

### 11.3. IDS-проверки

IDS используется для проверки:

- наличия обязательных свойств;
- допустимого класса IFC;
- значений и диапазонов свойств;
- требуемого профиля MICMTR;
- принадлежности к требуемому контексту ЖЦ;
- условий допуска к операции.

Пример логики:

```text
Если operation = documentation.release,
то требуется:
- lifecycle_code соответствует PIM-P-PP или PIM-P-PR;
- cde_state не ниже SHR или PUB, согласно политике;
- required_profile достигнут;
- статус проверки = verified;
- IDS-правила обязательных свойств пройдены.
```

## 13. Управление изменениями

### 13.1. Версионность

Используется Semantic Versioning:

```text
MAJOR.MINOR.PATCH
```

| Тип | Когда повышается |
|---|---|
| `MAJOR` | Несовместимое изменение структуры кодов, значений или обязательных полей |
| `MINOR` | Обратно совместимое добавление фаз, кодов, свойств, правил или приложений |
| `PATCH` | Исправление описаний, примеров и ошибок без изменения смысла |

### 13.2. Правила

1. Существующие коды не переопределяются без повышения `MAJOR`.
2. Новый жизненный цикл, стадия, этап или подэтап добавляется как расширение классификатора.
3. Нечётные уровни MICMTR остаются зарезервированными, пока не введены отдельной совместимой версией.
4. Required и Actual Profile всегда хранятся раздельно.
5. Неизвестное значение `null` не равно уровню `0`.
6. Любое изменение кода, профиля или состояния должно быть отражено в журнале изменений.
7. Матрица операций и требуемых профилей должна проверяться на реальных кейсах до перевода из Draft в Stable.

## 14. Границы версии 0.1.0

В эту версию включены:

- PIM/AIM;
- классификатор ЖЦ из принятой технологии информационного моделирования;
- типы ИМ;
- состояния СОД;
- структура MICMTR;
- Required/Actual Profile;
- стартовая матрица операционных ворот;
- базовая JSON-модель;
- связь с IFC/IDS.

В эту версию сознательно не включены как обязательные нормы:

- окончательная политика именования файлов;
- точные правила нумерации выпусков и ревизий;
- конкретные криптографические хеш-алгоритмы;
- полная модель ролей и ответственности;
- отраслевые расширения для дорог, РЖД, промышленности, атомной отрасли;
- окончательные профили для всех классов IFC и типов элементов;
- окончательные IDS-шаблоны.
