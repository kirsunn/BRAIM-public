# 1. Цель BAIM

BAIM рассматривается как цифровое ядро для описания информации об объекте строительства, пространстве, элементах, процессах, вариантах решений и допустимости операций над данными.

Предполагалось, что BAIM должен:

- работать независимо от конкретного авторского BIM-ПО;
- использовать IFC, IDS, CDE и внешние классификаторы через адаптеры;
- хранить структурированные данные об объекте, процессах, моделях и связях;
- поддерживать проектную (`PIM`) и эксплуатационную (`AIM`) информацию;
- поддерживать генератор планировок;
- проверять достаточность информации для конкретных операций;
- фиксировать происхождение вариантов и решений.

# 2. Источник методологических предпосылок

В качестве исходного материала использовался документ «Принятая технология информационного моделирования». Из него были взяты следующие идеи:

- информационная модель описывает объект, процесс, материал, механизм, ресурс или часть объекта;
- модель может включать данные, документы, словарь и требования;
- различаются дисциплинарные, объединённые, опорные, сводные, аналитические и параметрические модели;
- жизненный цикл здания/сооружения и жизненный цикл информационной модели различны, но связаны;
- CDE/СОД использует состояния разработки, совместного доступа, публикации и архива;
- PIM относится к проектной части ЖЦ, AIM — к эксплуатации и управлению активом;
- реконструкция использует сведения существующего актива как входные данные и запускает новую проектную работу.

# 3. BAIM-LIMS: исходное назначение

## 3.1. Наименование

```text
BAIM-LIMS
Building Asset Information Model — Lifecycle & Maturity Standard
```

В рабочей трактовке — стандарт описания состояния готовности информации о строительном объекте.

Заявленный вопрос системы:

```text
Насколько элемент проработан, достоверен и готов к операции?
```

Заявленные внешние системы, поверх которых предполагается строить измерительный слой:

```text
CoClass
CCS
КСИ
```

# 4. Профиль зрелости

## 4.1. Рабочий формат

```text
{NAMESPACE}:GE-IN-CO-MA-TO-RE
```

Пример:

```text
PIM:GE2-IN2-CO111-MA4444-TO4-RE444
```

## 4.2. Namespace

| Namespace | Рабочий смысл |
|---|---|
| `PIM` | Проектная информационная модель |
| `AIM` | Эксплуатационная информационная модель |
| `BAIM` | Единое пространство BAIM при необходимости |

В первоначальной логике `PIM` соответствует фазам концепции, проектирования и создания, а `AIM` — использованию и демонтажу. Это создаёт вопрос: namespace — самостоятельное поле или вычисляемый результат фазы/контекста.

## 4.3. Регистры

| Токен | Название | Рабочий смысл | Шкала |
|---|---|---|---|
| `GE` | Geometry | Геометрическая проработанность | `0,2,4,6,8,10` |
| `IN` | Information | Полнота атрибутивной информации | `0,2,4,6,8,10` |
| `CO` | Conformance | Соответствие геометрии, логики, информации | Триада `0,1,2` |
| `MA` | Maturity | Размер, форма, местоположение, ориентация | 4 позиции по `0..10` |
| `TO` | Tolerance | Точность / допуск | `0,2,4,6,8,10` |
| `RE` | Relationships | Полнота связей | `0,2,4,6,8,10` |

## 4.4. MA: четыре внутренние позиции

```text
MA = Size - Form - Location - Orientation
```

Рабочая запись:

```text
MA4444
```

означает, что размер, форма, положение и ориентация находятся на уровне 4.

## 4.5. CO: триада

Рабочее направление трёх цифр:

```text
геометрия → логика → информация
```

| Значение | Рабочий смысл |
|---|---|
| `0` | Не задано / не проверено |
| `1` | Соответствие проектному эталону |
| `2` | Подтверждение относительно факта или внешних данных |

Примеры:

```text
CO000 — не задано
CO100 — заявлено/проверено геометрическое соответствие на проектном уровне
CO111 — соответствует проектной модели
CO222 — заявлено как подтверждённое относительно факта
```

## 4.6. Required и Actual Profile

Ключевое разделение:

```text
Required Profile — минимально необходимый профиль для операции.
Actual Profile   — профиль, фактически присвоенный результату проверки.
```

Рабочий пример:

```json
{
  "required_profile": "PIM:GE2-IN2-CO111-MA4444-TO4-RE444",
  "actual_profile": "PIM:GE2-IN2-CO110-MA4444-TO4-RE444",
  "validation_status": "recheck_required"
}
```

## 4.7. Важное ограничение

Профиль не следует считать абсолютным постоянным свойством элемента. Рабочая формула для следующей итерации:

```text
Profile(element, context, operation, discipline, time)
```

Один элемент может быть достаточен для одной операции и недостаточен для другой.

# 5. Жизненный цикл

## 5.1. Фазы

| Код | Фаза |
|---|---|
| `C` | Концепция |
| `P` | Проектирование |
| `S` | Создание / строительство |
| `U` | Использование / эксплуатация |
| `D` | Демонтаж / утилизация |

## 5.2. Рабочие коды ЖЦ

```text
PIM-C-SUR     Инженерные изыскания
PIM-C-FS      Обоснование инвестиций
PIM-P-PR      Проектная документация
PIM-P-EX      Рабочая документация
PIM-S-CON     Строительно-монтажные работы
PIM-S-IE      Исполнительная модель / ввод
AIM-U-OPS     Эксплуатация
AIM-D-DEM     Демонтаж
```

## 5.3. Итерация

Рабочее положение:

```text
Реконструкция запускает новую итерацию жизненного цикла.
```

Формат:

```text
{ITER}:{PHASE}-{STAGE}
```

Примеры:

```text
0:S-CON
1:P-PR
0:D-DEM
0:U-OPS
```

Итерация `0` — исходный объект; итерация `1` — реконструкция; дальнейшие итерации — последующие изменения.

## 5.4. Пример параллельных контекстов квартиры

| Помещение | Итерация | Фаза | Код |
|---|---:|---|---|
| Комната 1 | 0 | Строится | `0:S-CON` |
| Комната 2 | 1 | Проектируется | `1:P-PR` |
| Комната 3 | 0 | Демонтируется | `0:D-DEM` |
| Комната 4 | 0 | Эксплуатируется | `0:U-OPS` |

Рабочая гипотеза: элементы/пространства одного актива могут одновременно участвовать в разных процессах и итерациях.

## 5.5. Критическое уточнение для следующей итерации

Нельзя без дополнительной модели утверждать, что «жизненный цикл хранится на элементе» как одно скалярное поле. Для одного элемента могут существовать несколько контекстов работ и использования.

Следует рассмотреть разбиение:

```text
Asset lifecycle state
Activity / work package participation
Information applicability
```

Итерации должны быть графом, а не просто числом:

```text
iteration_id
parent_iteration_id
scope
affected_elements
inherited_elements
merge_policy
```

# 6. Состояния СОД / CDE

Рабочий набор:

| Код | Смысл |
|---|---|
| `WIP` | В работе |
| `REV` | На проверке / согласовании |
| `SHR` | Совместный доступ |
| `PUB` | Утверждено / опубликовано |
| `ARC` | Архивировано |

Рабочий поток:

```text
WIP → REV → SHR → PUB → ARC
```

Возможные возвраты:

```text
REV → WIP
SHR → WIP
PUB → WIP только через новый выпуск; предыдущая опубликованная версия сохраняется как архивная.
```

Критическое замечание для следующей итерации: это повторяет значительную часть CDE-подхода ISO 19650. Нужно решить, является ли BAIM-LIMS владельцем этих статусов либо только хранит ссылку на внешнюю CDE policy.

# 8. Вариантность

## 8.1. Исходная иерархия

```text
Universe (проект)
  └── Galaxy (зона изменяемости)
        └── Foam (эфемерная среда генерации)
              └── Variant (сохранённый кандидат с GUID)
                    └── Decision (решение / результат слияния)
```

## 8.2. Исходные правила

1. Граница Galaxy определяется зоной изменяемости: комната, узел, система или другой изолированный фрагмент.
2. Foam существует внутри одной Galaxy и содержит временные кандидаты без постоянной идентичности.
3. Варианты из разных Galaxy не должны смешиваться без явно заданного правила.
4. GUID создаётся при сохранении кандидата как Variant.
5. Применялось правило `2+1`: два варианта сравниваются/согласуются, затем создаётся третий — синтезированный и доведённый до требуемой зрелости.

## 8.3. Статусы варианта

| Статус | Смысл |
|---|---|
| `proposed` | Предложен для сравнения |
| `active` | Проходит проверку |
| `result` | Результат синтеза/выбора, доводится до готовности |
| `rejected` | Отклонён |
| `archived` | Сохранён как история |

## 8.4. Рабочий пример

```json
{
  "galaxy_id": "room_01",
  "foam": {"rules": "...", "filters": "..."},
  "variants": [
    {"id": "V0", "status": "proposed", "profile": "GE2-IN2-CO111-MA4444-TO4-RE444"},
    {"id": "V1", "status": "proposed", "profile": "GE4-IN4-CO111-MA6666-TO6-RE666"}
  ],
  "result": {"id": "V2", "status": "result", "profile": "GE4-IN4-CO222-MA8888-TO8-RE888"}
}
```

## 8.5. Решение для дальнейшего пересоздания

В нормативном ядре предпочтительно заменить метафоры `Universe`, `Galaxy`, `Foam` на нейтральные технические сущности:

```text
VariantScope
Candidate
Variant
Decision
Derivation / Lineage
Merge
```

`VariantScope` задаётся изменяемым набором сущностей и не обязан совпадать с помещением.

```text
VariantScope
├── scope_id
├── parent_scope_id
├── affected_rooms[]
├── affected_zones[]
├── affected_elements[]
├── constraints[]
├── baseline_version
└── variants[]
```

## 8.6. Идентичность и происхождение

Нельзя считать GUID результата слияния автоматически равным GUID любого родителя. Необходимо различать:

```text
identity_guid      — идентичность сущности;
variant_guid       — идентичность альтернативы;
persistent_id      — идентичность физического объекта;
lineage            — происхождение результата;
parent_variant_ids — варианты-источники решения.
```

## 8.7. Комбинаторный риск

Если варианты независимы по зонам, число сочетаний растёт мультипликативно:

```text
N = n1 × n2 × ... × nk
```

Пример: 10 зон по 5 вариантов дают `5^10 = 9 765 625` комбинаций.

Для следующей итерации требуются механизмы:

```text
ограничение VariantScope
constraints
pruning
dominance rules
top-k / beam search
совместимость границ зон
memoization
```

Правило `2+1` допустимо только как UI/workflow-паттерн, а не как обязательный закон ядра до доказательства его необходимости.

# 9. Policy engine («дирижёр ядер»)

## 9.1. Заявленные функции

1. Проверять, достиг ли объект или набор данных Required Profile для операции.
2. Блокировать смешивание данных из несовместимых вариантов.
3. Связывать тип элемента с применимыми расчётами.
4. Поддерживать параллельные контексты элементов/пространств.

## 9.2. Минимальный инвариант

```text
Все входные сущности операции должны иметь совместимый variant_context,
операционный контекст, статус СОД и уровень подтверждения.
```

## 9.3. Что требуется определить

```text
- схема правил;
- входы и выходы;
- идентификатор операции;
- reason codes;
- протокол аудита;
- ручной override и обязательное обоснование;
- транзакционная модель;
- правила отката;
- provenance;
- определение compatible variant_context;
- выбор применимых расчётов по классификации и контексту.
```

До этого «дирижёр» является названием архитектурной идеи, но не реализуемой спецификацией.

# 10. Пространственная онтология: помещение и зона

## 10.1. Базовая формулировка

> **Помещение (комната) — сформированное строительными конструкциями пространство. Зона — функционально или технологически выделенная часть помещения или внешней территории, определяемая сценарием использования, размещением оборудования, мебели, проходами и эргономическими правилами. Конструкции формируют помещение; помещение содержит зоны; зоны не заменяют конструктивные границы помещения. Верхняя граница зоны может быть конструктивной или функциональной.**

## 10.2. Помещение

**Помещение** — сформированное строительными конструкциями трёхмерное внутреннее пространство, предназначенное для пребывания людей, размещения оборудования, выполнения функций или обслуживания здания.

Границы помещения образуются или задаются:

- стенами и перегородками;
- полом/перекрытием;
- потолком, покрытием или иной верхней границей;
- дверными, оконными и иными проёмами;
- явно определёнными виртуальными или условными границами, если это допускает проект.

Минимальная модель:

```text
Room
├── id
├── building_id
├── storey_id
├── parent_space_id
├── boundary_elements[]
├── footprint
├── volume
├── height
├── access_openings[]
├── name
├── intended_function
├── lifecycle_context
└── zones[]
```

## 10.3. Зона

**Зона** — функционально, технологически, эргономически или сценарно выделенная часть пространства. Для внутренних зон она принадлежит помещению; для внешних территорий применяется `SiteZone` или другой родительский пространственный контейнер.

Зона может определяться:

- функцией;
- деятельностью;
- мебелью;
- оборудованием;
- маршрутами;
- требованиями доступа;
- требованиями обслуживания;
- эргономическими правилами;
- ограничениями безопасности.

Минимальная модель:

```text
Zone
├── id
├── room_id | site_id
├── zone_type
├── geometry
├── function
├── activity[]
├── equipment[]
├── furniture[]
├── access_requirements[]
├── clearance_requirements[]
├── adjacency_requirements[]
├── overlap_policy
├── priority
└── validation_rules[]
```

## 10.4. Иерархия

```text
Здание / сооружение
  └── Секция / блок / этаж
        └── Квартира / арендуемая единица / функциональный блок
              └── Помещение (сформировано конструкциями)
                    └── Зона (функция, сценарий, эргономика)
                          └── Оборудование / мебель / проход / действие
```

Не все уровни обязательны.

## 10.5. Направление зависимости в генераторе

```text
Конструкции → помещение → зоны → размещение → сценарии использования
```

Допустимая обратная связь:

```text
требование зоны → необходимость изменить конструкцию → пересчёт помещения → пересчёт зон
```

Изменение стены должно пересчитывать контур помещения, его площадь и объём, все зависимые зоны, размещение мебели/оборудования и проходы.

## 10.6. Разделение и объединение помещений

```text
Room_A + Room_B → Room_C
Room_A → Room_A1 + Room_A2
```

При существенном изменении контура, состава границ или функции новая сущность не должна автоматически наследовать идентичность исходной. Необходима provenance-запись.

# 11. Функциональный объём зоны и верхняя граница

## 11.1. Основное решение

Уличная зона не является «зоной без верха».

> **Верхняя граница зоны может быть функциональной: минимально необходимая высота свободного пространства для заявленной деятельности.**

Эта граница существует даже при отсутствии потолка или иной физической конструкции.

## 11.2. Два вида верхней границы

| Тип | Смысл | Пример |
|---|---|---|
| Конструктивная | Физическое ограничение сверху | потолок, перекрытие, навес, пергола, крона |
| Функциональная | Требуемая высота свободного пространства | проход, прыжок, игра, спорт, обслуживание |

## 11.3. Функциональный объём

```text
Zone
├── id
├── parent_space_id
├── space_type: Indoor | SemiIndoor | Outdoor
├── functional_volume
│   ├── bottom_level
│   ├── required_height
│   ├── top_level = bottom_level + required_height
│   └── intrusion_rules[]
├── boundary_definition
│   ├── bottom: physical | virtual
│   ├── sides: physical | virtual | regulatory
│   └── top: physical | regulatory_plane | vegetation | canopy | none
└── ...
```

## 11.4. Примерные значения требуемой высоты

Это рабочие ориентиры, а не утверждённые нормативные значения:

| Тип зоны | Рабочая требуемая высота |
|---|---|
| Пешеходная зона | 2,20–2,50 м |
| Детская игровая зона 3–6 лет | 2,50–3,00 м |
| Детская игровая зона 7–12 лет | 3,00–4,00 м |
| Волейбольная площадка | от 7,00 м |
| Баскетбольная площадка | 7,00–8,00 м |
| Зона под деревьями | до нижней отметки крон с учётом функции |
| Зона под навесом | физическая высота конструкции, не ниже `required_height` |

## 11.5. Правило вторжения

Функциональный объём — защищённое пространство. В него могут вторгаться только объекты, разрешённые `intrusion_rules`.

```text
intrusion_rules[]
├── allowed_intrusion_type: vegetation | lighting | signage | temporary_structure
├── min_clearance_height
├── max_intrusion_depth
├── time_condition
└── safety_requirements
```

Примеры:

- ветви не должны опускаться ниже требуемой высоты пешеходной зоны;
- фонарь допустим при соблюдении требуемого зазора;
- временная сцена может занимать объём только при явно заданной временной политике;
- провода и кабели должны быть выше `top_level` либо иметь специальную защиту.

## 11.6. Пространственные типы

```text
Indoor     — закрытое пространство;
SemiIndoor — частично закрытое пространство: атриум, галерея, навес;
Outdoor    — открытое пространство: двор, площадка, парк, набережная.
```

Тип пространства влияет на интерпретацию верхней границы, применимые правила, климатические ограничения и допустимые вторжения.

# 12. Уличные, игровые и рекреационные зоны

## 12.1. Определение

**Уличная зона** — функциональная зона в пространстве `Outdoor`, у которой:

- нижняя граница — грунт, покрытие или фундамент;
- боковые границы — ограждения, бордюры, дорожки, рельеф, зелёные насаждения или виртуальные/регуляторные линии;
- верхняя граница — конструктивная, если есть навес, либо функциональная, если требуется свободная высота для деятельности.

## 12.2. Примеры

| Зона | `space_type` | Рабочая верхняя граница |
|---|---|---|
| Детская игровая площадка | `Outdoor` | функциональная плоскость, например 3,00 м |
| Волейбольная площадка | `Outdoor` | функциональная плоскость, от 7,00 м |
| Зона отдыха со скамейками | `Outdoor` | функциональная высота для прохода/использования |
| Набережная | `Outdoor` | функциональная высота пешеходного маршрута |
| Парк с дорожками | `Outdoor` | функциональная высота с контролем крон |

## 12.3. SiteZone

Для внешней территории вводится контейнер:

```text
SiteZone
├── id
├── site_id
├── zone_type: playground | recreation | sport | parking | green | etc.
├── geometry
├── function
├── equipment[]
├── functional_volume
│   ├── bottom_level
│   ├── required_height
│   └── top_level
└── validation_rules[]
```

`SiteZone` не является `Room.Zone`, но использует тот же принцип функционального объёма.

# 13. Генератор планировок

## 13.1. Последовательность работы

```text
1. Получить границы объекта, этажей и доступных конструктивных контуров.
2. Сформировать или принять конструктивные границы помещений.
3. Создать помещения как пространственные сущности.
4. Назначить помещениям требуемые функции.
5. Создать зоны по функциональным и эргономическим правилам.
6. Разместить оборудование и мебель в допустимых зонах.
7. Проверить проходы, открывания, доступность, соседство, площади и коллизии.
8. Создать кандидатов и сохранить допустимые варианты.
9. Сформировать решение и зафиксировать provenance.
```

## 13.2. Проверки помещения

```text
- Контур замкнут либо имеет явно установленный тип условной границы.
- Контур не самопересекается.
- Помещение принадлежит одному пространственному контейнеру выбранного уровня.
- Площадь и объём вычислимы.
- Границы ссылаются на конструкции или явные виртуальные границы.
- Доступность определяется через проёмы и маршруты.
```

## 13.3. Проверки зоны

```text
- Родительское пространство существует.
- Геометрия зоны находится внутри допустимой области родителя.
- Пересечение зон соответствует overlap_policy.
- Оборудование и мебель связаны с подходящими зонами.
- Требуемые проходы, сервисные зоны и зоны открывания не блокируются.
- Вторжения в functional_volume соответствуют intrusion_rules.
```

## 13.4. Пример пересчёта

```text
W-03 сдвигается на 0,60 м.
→ пересчитывается контур помещения R-01.
→ пересчитываются площадь и объём R-01.
→ пересчитываются зоны сна, хранения, прохода и рабочего места.
→ проверяется размещение кровати, шкафа, стола и проходов.
→ вариант сохраняется только после прохождения ограничений.
```

# 14. Связь с IFC, IDS и внешними стандартами

## 14.1. Принцип

BAIM должен быть платформонезависимым. Авторские системы (Renga, Revit, Archicad и др.) подключаются через коннекторы; канонические данные BAIM не должны зависеть от одного приложения.

## 14.2. Рабочий набор BAIM-свойств

```text
BAIM_LifecycleContext
BAIM_IterationId
BAIM_ModelType
BAIM_CDEState
BAIM_Release
BAIM_Revision
BAIM_RequiredProfile
BAIM_ActualProfile
BAIM_ValidationStatus
BAIM_IntendedUse
BAIM_ResponsibleParty
BAIM_VariantContext
BAIM_Provenance
```

## 14.3. IDS

IDS предполагается использовать для проверки:

- применимости требований к IFC-сущностям;
- обязательных свойств;
- типов данных;
- диапазонов и допустимых значений;
- наличия BAIM-метаданных;
- структурных ограничений поставки.

## 14.4. Нерешённый вопрос

Не доказано, что BAIM-LIMS должен дублировать возможности IFC + IDS + ISO 19650 CDE metadata + классификаторов. В следующей итерации необходимо определить конкретный уникальный разрыв, который BAIM закрывает.

# 15. Критическая рецензия: выводы, которые нельзя игнорировать

## 15.1. Статус BAIM-LIMS

BAIM-LIMS нельзя считать стабильным стандартом. Рабочий статус для пересоздания:

```text
Research Draft
```

## 15.2. Фатальные вопросы

1. Ортогональность измерений не доказана.
2. ЖЦ элемента нельзя задавать одним скалярным полем без модели участия в работах.
3. Итерация не может быть только номером: нужны ветвление, область действия, наследование и слияние.
4. Профиль зрелости контекстен и не является абсолютным свойством элемента.
5. Шкала 0–10 не имеет проверяемой семантики без evidence model и машиночитаемых тестов.
6. `CO222` не означает достоверный as-built без источника, метода, даты, покрытия, допуска и ответственного.
7. Формат строки профиля требует формальной грамматики и JSON Schema.
8. `GE`, `MA`, `TO`, `CO`, `RE` частично пересекаются по смыслу.
9. Вариантность не имеет решения комбинаторного взрыва.
10. GUID исходных вариантов и результата слияния требуют раздельной модели идентичности и происхождения.
11. Policy engine не определён как исполнимая система правил.
12. Маппинг на СП 333 не может быть простым эквивалентом одного профиля зрелости.
13. CDE-часть во многом повторяет ISO 19650 и нуждается в обосновании владения.

## 15.3. Повтор существующих систем

| Система | Что уже покрывает |
|---|---|
| ISO 19650 | PIM/AIM, CDE, состояния информации, обмен, ответственность, требования |
| IFC | сущности, геометрия, отношения, идентификаторы, обмен моделью |
| IDS | машиночитаемые требования к объектам и свойствам |
| ISO 12006-2 / CoClass / CCS / КСИ | классификация объектов, процессов, свойств, ресурсов и систем |
| СП 333 | уровни проработки ЦИМ в контексте стадии и требований |
| LOD/LOI/LOG | зрелость геометрии, информации и развития модели |

## 15.4. Минимум, который можно тестировать

Для следующей итерации предлагается тестировать не весь BAIM-LIMS, а минимум:

```text
contextual profile
+ CDE metadata
+ required/actual comparison
+ IDS validation
+ operation policy
```

# 17. Канонические фразы для восстановления

## 17.1. Помещение и зона

> Помещение (комната) — сформированное строительными конструкциями пространство.

> Зона — функционально или технологически выделенная часть помещения или внешней территории, определяемая сценарием использования, размещением оборудования, мебели, проходами и эргономическими правилами.

> Конструкции формируют помещение; помещение содержит зоны; зоны не заменяют конструктивные границы помещения.

## 17.2. Верхняя граница зоны

> Верхняя граница зоны может быть конструктивной — например, потолок или навес — либо функциональной: минимально необходимой высотой свободного пространства для заявленной деятельности.

> Уличная зона не является зоной без верха: её верхняя граница может быть нормативно-функциональной и задавать защищённый свободный объём для ходьбы, бега, прыжков, игр или спорта.

## 17.3. Контекстность зрелости

> Зрелость — не абсолютное свойство элемента. Она определяется относительно контекста, операции, дисциплины и времени.

## 17.4. Вариантность

> Вариантность должна хранить не только результат, но и происхождение: исходные данные, правила, ограничения, варианты-родители, выбор и результаты проверок.

## 17.5. Следующая итерация

> В следующей итерации BAIM должен быть пересоздан как набор согласованных формальных моделей, а не как единый документ, смешивающий жизненный цикл, CDE, зрелость, вариантность, онтологию пространства и policy engine.
