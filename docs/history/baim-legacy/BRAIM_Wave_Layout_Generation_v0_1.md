# Волновая генерация планировок + правила стыковки (наработки L16-GN)

> **Провенанс:** наработки автора из чата (Алиса/YandexGPT), найдены и сохранены 2026-10-16. Первый алгоритмический черновик для L16-GN (Generator, DEFERRED 2027+) и Режима Б «Генерация по ТЗ» (Concept v1.1 §1.3). Статус: reference material, не спецификация. Все нормативные значения — `needs_source` (R-05).

---

## 1. Цель и закрываемые риски

Цель BRAIM: автоматизировать проверку проектных решений на соответствие нормативам и сделать цепочку «норматив → правило → расчёт → доказательство» полностью воспроизводимой для экспертизы.

Ключевой риск: требования «всплывают» на экспертизе, потому что они не формализованы и не привязаны к данным проекта.

## 2. Ядро нормативов: граф критериев

Подход: из нормативов (СП, СанПиН, региональные НПА) извлекаются измеримые критерии и строятся зависимости.

Структура узла критерия: ID; текст требования; тип (площадь, инсоляция, эвакуация, доступность МГН и т.п.); метрика (м², часы, количество, уклон); порог (мин/макс/диапазон); источник (СП, статья, пункт); зависимости (на что влияет: планировка, фасад, лифты, парковка).

Пример:

```text
ID: NORM-54-123
Тип: площадь жилой комнаты
Метрика: м²
Порог: ≥ 14 м²
Источник: СП 54.13330.2022, п. 5.3.7
Зависимости: планировка секции, типовой этаж
```

Графовая модель (Neo4j-стиль):

```cypher
CREATE (n:Norm {id: "NORM-54-123", text: "Площадь жилой комнаты ≥ 14 м²", source: "СП 54.13330.2022 п. 5.3.7"})
CREATE (c:Criterion {id: "CRT-AREA-001", metric: "room_area", threshold_min: 14})
MERGE (n)-[:DEFINES]->(c)
```

## 3. Архитектура хранения: связка «файлы + БД»

| Компонент | Что хранит | Зачем |
|---|---|---|
| Файловое хранилище (S3 / сетевая папка) | Исходные документы (PDF/DOCX), отчёты, вложения, промежуточные CSV/Excel | Человекочитаемые артефакты для экспертизы и аудита |
| Графовая БД (Neo4j / ArangoDB) | Граф нормативов и критериев, правила валидации, связи «критерий → расчёт → файл» | Быстрое построение зависимостей и проверок |
| Реляционная БД (PostgreSQL) | Результаты расчётов, статусы, пользователи, логи, метаданные файлов | Надёжное хранение чисел, дат, флагов и версионирование |

Маппинг на примере: в БД хранится правило и результат (`room_area >= 14, status = OK, value = 15.2, calc_id = R-007`); в файлах — PDF СП и CSV с площадями комнат; в графе — связи норматив → критерий → расчёт → подтверждение.

## 4. Агенты (роли) и их задачи

| Агент | Входные данные | Выход | Критерии успеха |
|---|---|---|---|
| Лингвист | Текст норматива (СП, письма и т.п.) | Сырой критерий + пометка «требует уточнения» | Извлечены все требования, нет пропущенных пунктов |
| Распознаватель (таблицы/формулы) | Сырой критерий от Лингвиста | Машиночитаемое правило (JSON/выражение) + ссылка на источник | Правило можно автоматически применить к данным проекта |
| Диспетчер | Список задач и правил | Оркестрация проверок, выбор ветки правил при конфликте | Все объекты проверены, конфликты обработаны по приоритету |
| Кладовщик | Файлы, правила, результаты расчётов | Метаданные, версии, связи с графом, хранение файлов | Полная воспроизводимость: по результату можно найти исходный документ и правило |

Пример потока: Лингвист («есть таблица инсоляции, зависит от широты и ориентации фасада») → Распознаватель (таблица → формула/условие) → Диспетчер (запуск проверки по всем объектам) → Кладовщик (правило в графе + PDF-страница с таблицей + версия).

## 5. Волновая генерация планировки по контуру

Задача: на вход — контур здания (пятно застройки), на выход — нормативная планировка с расстановкой помещений.

Алгоритм (вариация BFS/алгоритма Ли):

1. **Сетка (grid).** Контур разбивается на ячейки (например, 0,3×0,3 м или 0,5×0,5 м).
2. **Источники «волн».** Точки-якоря: входные группы, лифтовые холлы, эвакуационные выходы, окна (для инсоляции).
3. **Распространение волны.** От якорей волна распространяется по ячейкам, присваивая «уровень удалённости». Топология: ближе к входу — коридоры/холлы, дальше — жилые комнаты, у окон — светлые зоны.
4. **Приоритеты и фильтры.** На каждом шаге проверяется, можно ли разместить помещение заданного типа: минимальная площадь; инсоляция (ориентация ячейки); доступ (непрерывная цепочка ячеек до выхода).
5. **Формирование комнат.** Когда волна «набирает» нужное количество ячеек с подходящими свойствами, они объединяются в помещение.

Это позволяет делать планировку нормативной с самого начала: коридоры нужной ширины, комнаты с доступом к свету, эвакуация.

## 6. Правила стыковки помещений: проёмы, коридоры, соединения

Принятые правила:

- **Доступность.** Каждое помещение имеет непрерывный путь до эвакуационного выхода: помещение → коридор → холл → выход.
- **Ширина проёма.** Минимум 0,8 м для жилых (эвакуация и пронос мебели). Для МГН и технических помещений — свои пороги.
- **Расположение проёма.** С учётом траектории движения, примыкания к коридору нужной ширины, исключения пересечения с несущими конструкциями (при наличии BIM-данных).
- **Коридоры.** Минимальная ширина 1,2 м (или по расчёту эвакуации); коридор — «транспортный слой», не фрагментируется.
- **Стыковка «комната–комната» без коридора.** В жилых домах запрещена для основных помещений; исключения фиксируются отдельными правилами.
- **Окна и ориентация.** Не менее 1 окна на жилую комнату; ориентация и площадь остекления — по СП.

Псевдокод валидации стыков:

```pseudo
for each room in generated_rooms:
    if not has_continuous_path_to_exit(room):
        mark_invalid(room, "Нет эвакуационного доступа")
    door = get_door(room)
    if door.width < 0.8:
        mark_invalid(door, "Ширина проёма < 0.8 м")
    corridor = get_adjacent_corridor(room)
    if corridor.width < 1.2:
        mark_invalid(corridor, "Коридор уже 1.2 м")
    if room.type == "жилая" and not has_window(room):
        mark_invalid(room, "Жилая комната без окна")
```

Граф связей стыковки (Neo4j-стиль):

```cypher
(r:Room {id:"ROOM-101", type:"жилая"})
-[:HAS_DOOR]->(d:Door {width:0.9})
-[:ADJACENT_TO]->(c:Corridor {width:1.4})
-[:LEADS_TO]->(e:Exit)
(r)-[:REQUIRES]->(w:Window)
```

## 7. Практические решения и ограничения

- Для BRAIM не используем «плоский» список требований — только граф зависимостей, чтобы видеть, как изменение одного параметра влияет на другие.
- Валидация строится как цепочка доказательств: норматив → правило → расчёт → файл-доказательство → статус.
- Графовая БД — для зависимостей; реляционная — для результатов и метаданных; файлы — для исходных документов и отчётов.

## 8. Блок 1. ТЗ: требования, критерии, стыковки (ссылки на нормативы)

*(значения — `needs_source`, подлежат подтверждению по первоисточникам перед включением в policy pack)*

| Критерий | Норматив | Формула проверки | Метрика |
|---|---|---|---|
| Площадь жилой комнаты ≥ 14 м² | СП 54.13330.2022, п. 5.3.7 | `room_area >= 14` | м² |
| Инсоляция жилых помещений ≥ 2 ч/день | СанПиН (гигиенические требования к инсоляции), СП 42.13330 | `insolation_hours >= 2` | часы |
| Ширина коридора ≥ 1,2 м | СП 1.13130 | `corridor_width >= 1.2` | м |
| Ширина дверного проёма ≥ 0,8 м | СП 59.13330, СП 1.13130 | `door_width >= 0.8` | м |
| Окно в каждой жилой комнате | СП 54.13330.2022, СП 42.13330 | `has_window = true` | булево |
| Непрерывный эвакуационный путь | СП 1.13130 | путь room → corridor → lobby → exit без разрывов | граф |
| Прямой доступ комната–комната запрещён | СП 54.13330.2022 | `direct_room_to_room_access = false` | булево |

Требования к стыковке: проём примыкает к коридору нормативной ширины; не пересекает несущие конструкции; коридор непрерывен без сужений ниже норматива; для каждого критерия — ссылка на пункт, формула проверки и файл-доказательство.

## 9. Блок 2. Прототип: псевдокод

**Шаг 1. Входные данные:** контур здания (полигон/DXF/IFC); сетка 0,3–0,5 м (Cell: координаты, occupied); якоря (входы, лифтовые холлы, эваковыходы, окна).

**Шаг 2. Волновая генерация (BFS):**

```pseudo
function generate_layout(contour, anchors, rules):
    grid = create_grid(contour, cell_size=0.3)
    wave_front = queue()
    for anchor in anchors:
        wave_front.push(anchor)
        grid[anchor].distance = 0
        grid[anchor].type = anchor.type

    while not wave_front.empty():
        cell = wave_front.pop()
        for neighbor in get_neighbors(cell, grid):
            if not neighbor.inside_contour or neighbor.occupied:
                continue
            if not can_place_room_type(neighbor, cell.distance, rules):
                continue
            neighbor.distance = cell.distance + 1
            neighbor.occupied = true
            wave_front.push(neighbor)

    rooms = cluster_cells_into_rooms(grid, rules)
    return rooms
```

**Шаг 3. Формирование помещений:** смежные ячейки, удовлетворяющие критериям (площадь, инсоляция, доступ), объединяются в Room; фиксируются тип, площадь, ячейки, ориентация по окнам, расстояние до выхода.

**Шаг 4. Валидация стыков:** эвакуационный доступ; ширина проёма; ширина коридора; окно в жилой; запрет прямой стыковки. Вывод ошибок с привязкой к ID комнат/проёмов и пунктам нормативов.

Практические шаги прототипа: сетка → BFS с фильтрами → кластеризация → валидация → отчёт ошибок.

## 10. Блок 3. Архитектура графа: типы узлов и связей

**Узлы:** `Norm` (id, text, source, section, is_active) · `Criterion` (id, metric, threshold_min/max, type) · `Room` (id, type, area, orientation, status) · `Door` (id, width, height, location) · `Corridor` (id, width, length, is_continuous) · `Exit` (id, location, capacity) · `Calculation` (id, value, status, file_path, page) · `Document` (id, path, hash, version).

**Связи:** `Norm-[:DEFINES]->Criterion` · `Criterion-[:APPLIES_TO]->Room` · `Room-[:HAS_DOOR]->Door` · `Door-[:ADJACENT_TO]->Corridor` · `Corridor-[:LEADS_TO]->Exit` · `Room-[:REQUIRES]->Window` · `Calculation-[:CONFIRMS]->Criterion` · `Calculation-[:BASED_ON]->Document`.

Пример запроса — все комнаты без эвакуационного доступа:

```cypher
MATCH (r:Room)
WHERE NOT (r)-[*..10]-(e:Exit)
RETURN r.id, r.type, r.area
```
