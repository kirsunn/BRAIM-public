# BAIM Ontology — Сводный стандарт

**Версия:** 1.0 (консолидированная)
**Статус:** Draft
**Дата:** 2026-09-30
**Основание:** IFC 4.3.2.0 (ISO 16739-1:2024), IFC5 / IFCX (dev), IDS 1.0, BCF API 3.0, СП 54.13330.2022

---

## 0. Аннотация

Настоящий документ консолидирует онтологическую модель **BAIM** для генератора планировок: помещения, зоны, вариантность и жизненный цикл. Ключевой результат сверки с семейством стандартов buildingSMART: **BAIM не является альтернативой IFC, а представляет собой слой над ним**. Пространственная онтология совпадает с IFC почти без потерь; собственный вклад BAIM локализован там, где IFC молчит.

---

## 1. Назначение и область применения

**Назначение:** онтологическая модель для генератора планировок BAIM.

**Масштаб:** два уровня — здание (помещения и зоны) и участок (внешние зоны и площадки).

**Входит в область:**
- пространственная иерархия здания и участка;
- помещение как пространственный объект;
- зона как функциональная, системная или групповая сущность;
- вариантность планировок;
- жизненный цикл и итерации;
- правила проверки и валидации.

**Не входит:**
- инженерные системы (MEP) в детализации;
- конструктивный расчёт;
- финансово-договорные сущности.

## 2. Терминология и границы понятий

```text
Конструкции формируют помещение.
Помещение содержит зоны.
Зоны описывают сценарии использования пространства.
```

**Помещение не является зоной, а зона не является помещением.**

| Понятие | Природа | Геометрия | IFC-аналог |
|---|---|---|---|
| Конструкция | материальная | есть | `IfcElement` (стена, перекрытие) |
| Помещение | пространственная | есть | `IfcSpace` |
| Функциональная зона | материальная, авторская | есть | `IfcSpatialZone` + Pset |
| Системная зона | материальная, выведенная | есть | `IfcSpatialZone` (тип) |
| Группа (квартира) | нематериальная | нет | `IfcZone` |
| Оборудование / мебель | материальная | есть | `IfcFurnishingElement` |
| Сценарий | производная | нет | нет |

**Ключевое различие:** «зона» — перегруженный термин. Под ним живут три сущности с разной природой: **разбиение** (функциональная), **суперпозиция** (системная), **членство** (группа).

## 3. Пространственная иерархия

```text
Здание / сооружение
  └── Секция / блок / этаж
        └── Квартира / арендуемая единица / функциональный блок
              └── Помещение (сформировано конструкциями)
                    └── Зона (функция, сценарий, эргономика)
                          └── Оборудование / мебель / проход / действие
```

Не все уровни обязательны. Примеры цепочек:

```text
Жилой объект:      Здание → секция → квартира → помещение → зона
Общественный:      Здание → этаж → помещение → зона
Внешняя территория: Участок → SiteZone
```

**Механизмы связи уровней (разной природы):**

| Переход | Механизм | IFC |
|---|---|---|
| Здание → Секция → Этаж | декомпозиция | `IfcRelAggregates` |
| Этаж → Помещение | контейнирование | `IfcRelContainedInSpatialStructure` |
| Квартира ← Помещения | группировка (ссылка) | `IfcRelAssignsToGroup` |
| Помещение → Зона | контейнирование | `IfcRelContainedInSpatialStructure` |
| Зона → Зона | агрегация | `IfcRelAggregates` |

## 4. Помещение

### 4.1. Определение

**Помещение (комната)** — сформированное строительными конструкциями трёхмерное внутреннее пространство, предназначенное для пребывания людей, размещения оборудования, выполнения функций или обслуживания здания.

Помещение образуется границами, которые создаются или задаются:
- стенами и перегородками;
- перекрытием и полом;
- потолком, покрытием или иной верхней границей;
- дверными, оконными и иными проёмами;
- при необходимости — условными границами, явно определёнными проектом.

### 4.2. Обязательные признаки

```text
1. Пространственный объём или определяемая область пола.
2. Контур, сформированный или ограниченный конструкциями.
3. Принадлежность к объекту более высокого уровня.
4. Уникальный идентификатор.
5. Геометрическое представление или вычислимый контур.
```

### 4.3. Свойства помещения

```text
Room
├── id
├── building_id
├── storey_id
├── parent_space_id
├── boundary_elements[]
├── footprint
├── volume
├── height
├── access_openings[]
├── name
├── intended_function
├── is_external                 # внутреннее/внешнее (см. 10.2)
├── predefined_type             # функциональная категория
├── lifecycle_context
└── zones[]
```

### 4.4. Последствия изменения конструкций

```text
Перенос перегородки → меняется контур одного или нескольких помещений.
Заделка дверного проёма → меняется доступность помещения.
Устройство новой перегородки → помещение может быть разделено на два.
Демонтаж перегородки → два помещения могут быть объединены в одно.
```

Происхождение результата фиксируется явно:

```text
Room_A + Room_B → Room_C
Room_A → Room_A1 + Room_A2
```

Идентичность нового помещения не считается автоматически идентичностью исходного, если контур, состав границ или функция изменились существенно.

### 4.5. Типы границ

```text
physical    # физическая конструкция
virtual     # условная, явно заданная проектом
functional  # функциональное деление
regulatory  # нормативная граница
```

Условная граница помещения не должна смешиваться с границей зоны.

## 5. Зона

### 5.1. Определение и три класса

**Зона** — выделенная часть пространства, определяемая назначением, деятельностью, оборудованием, маршрутами или правилами. В зависимости от природы различаются три класса:

| Класс | Примеры | Геометрия | Пересечение | Охват |
|---|---|---|---|---|
| **Функциональная** | сон, готовка, хранение | авторская | **запрещено** | одно помещение |
| **Системная** | вентиляция, тепло, свет | выведенная | **разрешено** | много помещений |
| **Группа** | квартира, пожарный отсек | **нет** | — | много помещений |

### 5.2. Функциональная зона

Существует внутри одного помещения. Задаётся автором. Дизъюнктна с другими функциональными зонами. Примеры:

```text
Спальня:   зона сна; зона хранения; зона прохода; рабочая зона.
Кухня:     зона приготовления; зона мойки; зона хранения; обеденная зона.
Санузел:   зона унитаза; зона умывальника; зона душа; зона обслуживания.
```

### 5.3. Системная зона

Существует **над** помещениями. Геометрия **выводится** из связности (например, через проёмы) и пересчитывается при изменении топологии. Может накладываться на функциональные и на себе подобные.

```text
Пример: объём помещений без заполнения проёмов, объединённый
в один воздушный объём для расчёта вентиляции.
```

### 5.4. Группа

Не имеет геометрии. Группирует помещения и/или зоны. Паспорт группы **вычисляется** по правилам норматива, а не хранится как атрибут.

```text
Пример: квартира A-12 как группа помещений; паспорт по СП 54.13330.2022.
```

### 5.5. Свойства зоны

```text
Zone
├── id
├── class                       # FUNCTIONAL | SYSTEM | GROUP
├── room_id                     # для FUNCTIONAL; для SYSTEM/GROUP — связи
├── zone_type
├── geometry                    # авторская (FUNCTIONAL) | выведенная (SYSTEM)
├── function
├── activity[]
├── equipment[]
├── furniture[]
├── access_requirements[]
├── clearance_requirements[]
├── adjacency_requirements[]
├── overlap_policy              # ALLOW | DISALLOW | CONDITIONAL
├── priority
├── functional_volume           # см. раздел 7
└── validation_rules[]
```

### 5.6. Принципы

1. Функциональная зона принадлежит одному помещению в пределах версии.
2. Одно помещение может содержать ноль, одну или множество функциональных зон.
3. Системные зоны пересекаются свободно; функциональные — нет.
4. Зона может быть геометрической, параметрической или вычисляемой.
5. Зона может быть временной (открывание двери, обслуживание, эвакуация).
6. Зона не создаёт помещение и не заменяет конструктивную границу.

## 6. Инварианты зонирования

### 6.1. Вложенность

```text
∀ zone ∈ FUNCTIONAL:  zone.room_id существует
                      ∧ zone.geometry ⊆ room.geometry
```

Зона не выходит за помещение и, следовательно, за квартиру.

### 6.2. Непересечение

```text
∀ z1, z2 ∈ FUNCTIONAL, z1 ≠ z2:  area(z1 ∩ z2) = 0
```

Справедливо для функциональных зон. Системные зоны пересекаются свободно.

### 6.3. Граница и отделка

```text
zone.outer_limit = room.finished_boundary   # чисто́вая поверхность
```

Нормативная площадь помещения измеряется до чистовой поверхности, минус выступающий декор (плинтусы, короба, декор не учитываются). Отделка лежит внутри этой границы и своей толщиной в площадь не входит.

### 6.4. Площадь и остаток

```text
Σ area(zone) ≤ area(room)          # равенство НЕ требуется
residual = area(room) − Σ area(zone) ≥ 0
```

**Зоны не образуют разбиение помещения.** Они образуют разбиение подмножества помещения. `residual` — незонированная область; вводится явно, чтобы валидатор отличал «ещё не зонировано» от «забыли зонировать».

### 6.5. Сводка инвариантов

```text
1. Вложенность:     Zone ⊆ Room.
2. Непересечение:   функциональные зоны попарно дизъюнктны.
3. Граница:         предел зоны = чистовая граница помещения.
4. Площадь:         Σ A_zone ≠ A_room; residual ≥ 0.
```

Инварианты 2 и 4 — **view-level restriction**, а не свойство схемы IFC: IFC их не запрещает, а делегирует определению вида. Оформляются как правила валидации BAIM (профиль IDS).

## 7. Функциональный объём и верхняя граница

### 7.1. Два типа верхней границы

| Тип | Описание | IFC-аналог |
|---|---|---|
| **Конструктивная** | физическое ограничение сверху (потолок, навес, крона) | `Gross Height` |
| **Функциональная** | требуемая высота свободного пространства | `Clear Height` |

**Функциональная граница** существует даже там, где нет физической конструкции. Она определяется требуемой высотой для деятельности, а не материалом.

### 7.2. Формализация и разделение «факт / требование»

```text
Zone
├── functional_volume          # ФАКТ
│   ├── bottom_level
│   ├── top_level_actual       # вычисляется из геометрии
│   └── boundary_definition
├── requirement                # ТРЕБОВАНИЕ (Pset / IDS)
│   └── required_clear_height
└── intrusion_rules[]          # ПРАВИЛО
```

**Принципиально:** `required_clear_height` (норма) и `top_level_actual` (измерение) — разной природы. Их нельзя держать в одной структуре: это ровно та болезнь «норма в геометрии», за которую профиль отклоняется на рецензии. Требование проверяется против факта.

### 7.3. Примеры требуемой высоты

| Тип зоны | `required_height` (мин.) | Обоснование |
|---|---|---|
| Пешеходная зона (взрослые) | 2,20 м | безопасный проход |
| Пешеходная зона (общественная) | 2,50 м | запас для маломобильных групп |
| Игровая зона (дети 3–6 лет) | 2,50–3,00 м | прыжки, простые игры |
| Игровая зона (дети 7–12 лет) | 3,00–4,00 м | активные игры |
| Спортивная площадка (волейбол) | 7,00 м | траектория мяча |
| Спортивная площадка (баскетбол) | 7,00–8,00 м | полёт мяча, кольцо |
| Зона с деревьями | до нижней отметки крон | ветви не мешают функции |
| Зона с навесом / перголой | высота конструкции | должна удовлетворять `required_height` |

### 7.4. Правила вторжения

```text
intrusion_rules[]
├── allowed_intrusion_type: vegetation | lighting | signage | temporary_structure
├── min_clearance_height
├── max_intrusion_depth
├── time_condition          # постоянно / временно / сезонно
└── safety_requirements
```

Примеры: фонарь — при высоте подвеса ≥ 2,50 м; ветви дерева — не ниже 2,20 м над дорожкой; временная сцена — с демонтажом после мероприятия.

### 7.5. Проверки

```text
- bottom_level определён.
- required_clear_height задан согласно функции.
- top_level_actual вычисляется корректно.
- Постоянные конструкции не вторгаются сверх intrusion_rules.
- Временные объекты учитываются.
- Для Outdoor top_level не обязан быть физической конструкцией.
```

## 8. Вариантность

### 8.1. Граница вариантности

```text
VariantScope
├── scope_id
├── parent_scope_id
├── affected_rooms[]
├── affected_zones[]
├── affected_elements[]
├── constraints[]
├── baseline_version
└── variants[]
```

Помещение часто является удобной границей вариантности, но не является ею автоматически.

### 8.2. Происхождение

```text
Candidate → Variant → Decision
```

Кандидаты, созданные и отброшенные генератором, не получают постоянной идентичности. Идентификатор создаётся, когда вариант сохранён для сравнения, проверки или решения.

```text
Decision
├── id
├── parent_variant_ids[]
├── selected_rules[]
├── basis                    # мотивировка выбора (вклад BAIM)
├── rejected[]               # что отвергнуто (вклад BAIM)
├── resulting_room_changes[]
├── resulting_zone_changes[]
├── resulting_placement_changes[]
└── validation_result
```

### 8.3. Вариант как слой

**Вариант — это слой, а не запись в базе.** В IFC5/IFCX вариант реализуется оверлеем поверх базового файла: свойства верхнего слоя перекрывают нижний. Откат — отключение оверлея.

```text
База (baim-base.ifcx.json)        → факты, инварианты
Оверлей (baim-overlay-variant)    → правки варианта, требования
```

## 9. Жизненный цикл и итерации

IFC хранит только последнее изменение (`IfcOwnerHistory`) и не моделирует историю. Поэтому ЖЦ реализуется **вне** IFC — как набор слоёв, накладываемых по времени. Каждая фаза — слой; перенос стены — оверлей поверх базы.

## 10. Маппинг на IFC 4.3.2.0 (ISO 16739-1:2024)

### 10.1. Таблица соответствий

| BAIM | IFC 4.3 | Механизм | Статус |
|---|---|---|---|
| Здание / сооружение | `IfcBuilding` (⊂ `IfcFacility`) | `IfcRelAggregates` | совпадает |
| Секция / блок | `IfcFacilityPart` + `UsageType` | `IfcRelAggregates` | совпадает |
| Этаж | `IfcBuildingStorey` (⊂ `IfcFacilityPart`) | `IfcRelAggregates` | совпадает |
| Квартира | `IfcZone` | `IfcRelAssignsToGroup` | совпадает |
| Помещение | `IfcSpace` | `IfcRelContainedInSpatialStructure` | совпадает |
| Внутреннее / внешнее | `Pset_SpaceCommon.IsExternal` | свойство | совпадает |
| Категория помещения | `IfcSpaceTypeEnum` | атрибут | совпадает |
| Условная граница | `IfcVirtualElement` | объект | совпадает |
| Граница помещения | `IfcRelSpaceBoundary` (2 уровня) | отношение | совпадает |
| Стена в двух комнатах | 2× `IfcRelSpaceBoundary` на один `IfcWall` | отношение | совпадает |
| Слои стены (ядро/отделка) | `IfcMaterialLayerSet(+Usage)` | набор | совпадает |
| Чистовая отделка | `IfcCovering` + `IfcRelCoversSpaces` | отношение | совпадает |
| Функциональная зона | `IfcSpatialZone` + BAIM Pset | containment | расширение |
| Системная зона | `IfcSpatialZone` (`VENTILATION`/`THERMAL`/…) | containment | совпадает по контейнеру |
| Владелец слоя | — | BAIM Pset | расширение |
| Вариантность | — | слои (IFC5) | расширение |
| ЖЦ и итерации | — | внешний слой | расширение |
| Зрелость / профиль | — | профиль IDS | расширение |

### 10.2. Критично: две оси пространства

`IfcSpace.PredefinedType` (ранее `InteriorOrExteriorSpace`) — **устаревшее** использование для «внутреннее/внешнее». Теперь:

```text
Внутреннее / внешнее   → Pset_SpaceCommon.IsExternal
Функциональная категория → IfcSpaceTypeEnum (SPACE | GFA | PARKING | ...)
```

Это **две разные оси**. Их нельзя сводить в одно поле.

### 10.3. Границы — объектами

Границы помещения определяются как объекты, а не только отношения: каждая граница ссылается на свой элемент. Так стена в двух комнатах описывается двумя границами на один `IfcWall`.

### 10.4. Зоны — контейнирование, не декомпозиция

`IfcSpatialZone` включается в иерархию через `IfcRelContainedInSpatialStructure`; зона-в-зоне — через `IfcRelAggregates`. Вложенность «помещение → зона» реализуется **контейнированием**, а не декомпозицией.

## 11. Маппинг на IFC5 / IFCX

### 11.1. Три основы IFCX

1. **ECS** — объект как сборка компонентов (геометрия, материал, свойства отдельно).
2. **Композиция из слоёв** — сцена собирается из файлов; верхний слой перекрывает нижний.
3. **USD** — геометрия (меши, `Xform`) и терминология (`Class`/`Def`/`Over`/`Inherits`).

### 11.2. Структура узла

```json
{
  "path": "<space-r01>",
  "children": {},
  "attributes": {
    "bsi::ifc::class": {"code": "IfcSpace"},
    "bsi::ifc::prop::IsExternal": false,
    "bsi::ifc::prop::PredefinedType": "SPACE",
    "baim::room::intended_function": "bedroom"
  }
}
```

Собственные атрибуты живут в пространстве имён `baim::` рядом с `bsi::ifc::`. Это и есть «свой Pset» в IFCX — не отдельный объект, а атрибуты в своём неймспейсе.

### 11.3. Слои


## 12. Реестр закрытых дыр

| Дыра (исходно) | Чем закрыта |
|---|---|
| «IFC не знает зон» | `IfcSpatialZone` (в т.ч. тип `VENTILATION`) |
| «Отделка не описана» | `IfcCovering` + `IfcRelCoversSpaces` |
| «Стена в двух комнатах не описана» | `IfcRelSpaceBoundary` (два на один элемент) |
| «Квартира как сущность» | `IfcZone` (без геометрии, паспорт вычисляется) |
| «Секция / блок» | `IfcFacilityPart` + `UsageType` |
| «Внутреннее / внешнее» | `IsExternal` (не `PredefinedType`) |
| «Вариантность» | слои IFCX (оверлеи) |
| «ЖЦ и фазы» | слои (temporal data в roadmap IFC5) |
| «Слои стены» | `IfcMaterialLayerSet` + ECS-компоненты |
| «Требование vs факт» | разделение слоёв (база = факт, оверлей = требование) |

**Вывод:** большая часть дыр закрыта стандартом. Собственный вклад сократился до локализованного набора (раздел 13).

## 13. Уникальный вклад BAIM

Остаётся там, где IFC и IFC5 молчат:

1. **Сценарная семантика зоны** — сценарий, эргономика, оборудование, проходы. IFC даёт контейнер и геометрию, но не семантику.
2. **Разделение «требование / факт»** — `required_clear_height` против `top_level_actual`. Модели требований в IFC нет.
3. **Provenance решения** — `Decision` с мотивировкой (`basis`) и отвергнутым (`rejected`). IFCX показывает, *какие* слои перекрыли, но не *почему* выбран вариант.
4. **Правила вторжения** в функциональный объём зоны — аналога нет.
5. **Владелец слоя** (помещение / зона) — IFC знает слои, но не их принадлежность.
6. **Инварианты зонирования** (вложенность, дизъюнктность, `Σ A_zone ≠ A_room`) — как профиль IDS.

## 14. Проверки и валидация

### 14.1. Помещение

```text
- Контур замкнут или имеет явный тип условной границы.
- Контур не самопересекается.
- Помещение принадлежит ровно одному контейнеру выбранного уровня.
- Площадь и объём вычислимы.
- Границы ссылаются на существующие конструкции или виртуальные границы.
- Доступность определяется через проёмы и маршруты.
```

### 14.2. Зона

```text
- room_id существует (для FUNCTIONAL).
- Геометрия внутри допустимой области помещения.
- Пересечение соответствует классу и overlap_policy.
- Оборудование и мебель связаны с подходящими зонами.
- Требуемые проходы и открывания не блокируются.
- Зона не выходит за конструктивную границу помещения.
```

### 14.3. Генерация

```text
- Вариант не нарушает неизменяемые ограничения.
- Перенос стены → пересчёт помещений и всех зависимых зон.
- Перенос оборудования → пересчёт связанных зон и маршрутов.
- Сохранённый вариант содержит provenance.
```

### 14.4. Механизм

Валидация выполняется через **IDS 1.0** (Information Delivery Specification): машиночитаемые требования, шесть типов фасетов, кардинальность Required / Optional / Prohibited. Специфические правила BAIM (инварианты зон, зрелость, вариантность) оформляются как **профиль IDS**, а не второй стандарт.
