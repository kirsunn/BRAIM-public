# BAIM-LIMS × IFC5 — карта соответствий и точки новизны

**Назначение:** сверка онтологии BAIM-LIMS с IFC5 (IFCX / ECS) и полным стеком buildingSMART.
**Статус:** рабочий документ
**Дата:** 2026-09-30

---

## 1. Что такое IFC5 — шесть сдвигов

| # | Сдвиг | Суть |
|---|---|---|
| 1 | **ECS** (Entity Component System) | Объект собирается из независимых компонентов: геометрия, материал, свойства, пространственная связь. Стена — не один объект, а композиция. |
| 2 | **IFCX** (JSON) | Уход от STEP/EXPRESS к JSON. Формат-агностик: XML, JSON, RDF, HDF5. |
| 3 | **Слои и оверлеи** | Сцена собирается из нескольких файлов-слоёв. Правка накладывается поверх базы, не изменяя её. «Higher layer wins». |
| 4 | **USD-выравнивание** | Композиция, «prim»-дерево, треугольные меши, наследование type → instance. IFC — семантика, USD — визуализация. |
| 5 | **Модульное ядро + расширения** | Core (domain-neutral) + доменные модули + отраслевые практики. Обновления модулей независимы. |
| 6 | **Late binding + мультиавторность + AI-native** | Часть схемы разрешается в рантайме; несколько авторов вносят данные параллельно; схема проектируется под ML. |

## 2. Карта: сущность BAIM → IFC5

| BAIM | IFC5 / IFCX | Статус |
|---|---|---|
| Здание / секция / этаж | Spatial hierarchy: `children` + `inherit` (Project → Site → Building → Storey) | совпадает |
| Помещение | `IfcSpace` (как компонент-сущность) | совпадает |
| Граница помещения | `IfcRelSpaceBoundary` | совпадает |
| Квартира | `IfcZone` (группировка, без геометрии) | совпадает |
| Системная зона (вентиляция, тепло) | `IfcSpatialZone` (overlapping) | совпадает |
| Функциональная зона (сон, готовка) | `IfcSpatialZone` + BAIM Pset | **расширение** |
| Отделка | Отдельный компонент / `IfcCovering` | совпадает как паттерн |
| **Вариантность** | **Слои / оверлеи IFCX** | **совпадает — механизм найден** |
| **Жизненный цикл / фазы** | **Слои (temporal data — цель roadmap)** | **частично совпадает** |
| Provenance решения (почему выбран вариант) | `explain_layer_history` — история слоёв, но **не мотивировка** | **расширение** |
| Требование vs факт (required_height) | Разные компоненты, но **нет модели требований** | **расширение** |
| Валидация (непересечение зон) | view restriction / IDS | **расширение** |
| Зрелость / CO | нет | **расширение** |

## 3. Главное совпадение: вариантность = слои

IFC5 собирает сцену из нескольких файлов-слоёв. База — один файл, правки — оверлеи,
которые перекрывают базу по приоритету.

```text
base.ifcx        ← базовая планировка
overlay_1.ifcx   ← вариант A (перекрывает базу)
overlay_2.ifcx   ← вариант B
phase_3.ifcx     ← фаза жизненного цикла
```

**Что это значит для BAIM:**
- `Candidate` = слой, который ещё не сохранён;
- `Variant` = сохранённый слой;
- `Decision` = слой + запись мотивировки (это надо добавить);
- `baseline_version` = базовый слой;
- фаза ЖЦ = отдельный слой-надстройка.

Механизм вариантов изобретать не нужно — он встроен.

## 4. Что снимается как «уже есть»

| BAIM-изобретение | Чем закрывается в IFC5 |
|---|---|
| Разделение стены на слои | ECS: геометрия / материал / свойства — компоненты |
| Общая стена в двух комнатах | `IfcRelSpaceBoundary` (2 ссылки на один элемент) |
| Владелец слоя (ядро / отделка) | Компонентная сборка + Pset |
| Вариантность планировок | Слои / оверлеи IFCX |
| Фазы ЖЦ | Слои (temporal data — цель roadmap IFC5) |
| Квартира как группа | `IfcZone` |
| Системная зона (воздух) | `IfcSpatialZone` с типом `VENTILATION` |

## 5. Где BAIM реально добавляет — пять точек

### 5.1. Сценарная (функциональная) зона
IFC5 даёт контейнер `IfcSpatialZone`, но не семантику: сценарий, эргономику,
оборудование, проходы. Это остаётся расширением BAIM (Pset + правила).

### 5.2. Требование vs факт
IFC5 разводит компоненты, но **модели требований нет**. `required_height` (норма)
и `top_level` (измерение) должны быть разными сущностями. Это твоё.

### 5.3. Provenance решения
IFC5 умеет показать, **какие** слои что перекрыли (`explain_layer_history`),
но не **почему** вариант выбран и какие отвергнуты. `Decision` с мотивировкой — твоё.

### 5.4. Валидация как view restriction
Непересечение функциональных зон IFC **не запрещает** — делегирует view.
Твоё правило дизъюнктности — законное расширение уровня view / IDS.

### 5.5. Функциональный объём с правилами вторжения
`intrusion_rules` (что допустимо в защищённом объёме зоны) — в IFC5 аналога нет.

## 6. Полный стек buildingSMART и место BAIM

```text
Данные        → IFC5 (IFCX, ECS)          ← BAIM берёт как фундамент
Требования    → IDS 1.0                    ← BAIM маппит свои CO сюда
Словарь       → bSDD                       ← BAIM Pset регистрирует здесь
Замечания     → BCF 3.0 (API)              ← BAIM связывает с зонами
API           → IFC5 API (в разработке)    ← точка интеграции BAIM
```

BAIM встаёт **над** стеком: берёт IFC5 как данные, IDS как проверку,
bSDD как словарь и добавляет сценарную зону, требования, provenance и ЖЦ.

## 7. Риски

1. **Alpha.** IFC5 не продакшн: «Incomplete Features», «Evolving Schema», «Non-Production».
   Строить на нём сегодня нельзя — только проектировать совместимость.
2. **Разрешение конфликтов слоёв.** «Higher layer wins» — простое правило,
   но при трёх авторах (каркас, R1, R2) нужен порядок приоритетов.
3. **Graph-модель.** IFC5 — сеть связей, реляционные БД не подходят;
   нужна graph-БД или RDF-хранилище.
4. **Потеря семантики при меш-геометрии.** Треугольные меши упрощают,
   но могут терять проектное намерение (параметрику).

---

## 8. Что делать

1. **Не изобретать вариантность** — взять слои IFC5 и добавить только `Decision`-мотивировку.
2. **Развести требование и факт** в зоне — до того, как писать Pset.
3. **Оформить BAIM Pset** для сценарной зоны и зарегистрировать в bSDD.
4. **Свести CO к IDS** там, где это возможно; оставить своё только для зрелости.
5. **Следить за IFC5-development** — попасть в обсуждение типов зон (запрос на расширение уже есть).
