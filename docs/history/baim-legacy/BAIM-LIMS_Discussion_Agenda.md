# BAIM-LIMS — повестка обсуждения

**Назначение:** список утверждений, выносимых на согласование, и реестр незакрытых пробелов.
**Дата:** 2026-09-30
**Основание:** BAIM-LIMS v1.0, враждебная техническая рецензия, онтология «Помещения и зоны», рабочая переписка.
**Статус документа:** рабочая повестка. Не является стандартом.

---

## 0. Рамка

Главный вывод рецензии принимается: **v1.0 не является стабильным стандартом**. Предлагается понизить статус до `1.0.0-draft` (Research Draft), сохранив номер 1.0 как отметку смены онтологии.

Версия и статус — разные оси:

| Ось | Вопрос | Значение |
|---|---|---|
| Версия | Насколько крупный сдвиг | 1.0 — сменилась онтология |
| Статус | Насколько проверено | Research Draft |
| Веха | Какое событие | M1–M3 |

Вехи: **M1** Вариантная вселенная · **M2** Помещение и зоны · **M3** Отделка как слои.

---

## Часть 1. Утверждения на обсуждение

Каждое утверждение — тезис, по которому нужно решение. Колонка «Решение» заполняется на встрече.

### A. Онтология пространства

| № | Утверждение | Почему на обсуждении | Решение |
|---|---|---|---|
| A1 | Конструкции формируют помещение; помещение содержит зоны; зона не заменяет конструктивную границу. | Базис всей модели | |
| A2 | Помещение может существовать без зон; зона без помещения недопустима для внутреннего пространства. | Определяет обязательность сущностей | |
| A3 | Зона, охватывающая несколько помещений, моделируется как `FunctionalGroup`, а не как зона с несколькими `room_id`. | Меняет способ описания общих функций | |
| A4 | Условные границы помещения допустимы и имеют тип `physical | virtual | functional | regulatory`. | Нужно для открытых планировок | |
| A5 | `SiteZone` — отдельная сущность, не `Room.Zone`. | Разводит территорию и здание | |
| A6 | Изменение конструкции меняет помещение как объект; идентичность нового помещения не наследуется автоматически. | Влияет на provenance и GUID | |

### B. Отделка и слои (в документах отсутствует — требуется внести)

| № | Утверждение | Почему на обсуждении | Решение |
|---|---|---|---|
| B1 | Отделка — слоистая структура, а не свойство стены. | Закрывает конфликт «стена в двух комнатах» | |
| B2 | Владелец чернового слоя — помещение; владелец чистового слоя — зона (через назначение). | Определяет, кто задаёт фазу | |
| B3 | У отделки две связи: физическая (`physical_context`) и функциональная (`functional_use`). | Стабильное и изменяемое нельзя смешивать | |
| B4 | Фаза слоя вычисляется от контекста-владельца, а не хранится в слое. | Снимает фазный конфликт как класс | |
| B5 | Развести три оси: представление (MVD), материал (слой), структурная роль (несущая/ненесущая). | В переписке они были слиты в одно слово «слой» | |
| B6 | Назначение слоя датируется (`assigned_at`, `basis`). | Разрывает взаимную зависимость зона ↔ отделка | |

### C. Профиль

| № | Утверждение | Почему на обсуждении | Решение |
|---|---|---|---|
| C1 | Профиль — контекстная функция `Profile(element, operation, discipline, context, time)`, а не постоянное свойство. | Снимает конфликт законных оценок одного элемента | |
| C2 | Разделить «измерение» (что есть) и «требование» (что нужно). | Убирает смешение в регистрах | |
| C3 | Каждому уровню шкалы — признаки, источник доказательства, машинный тест, ответственная роль. | Превращает маркировку в измерение | |
| C4 | `CO` сохраняется только с доказательной моделью (`reference_type`, `reference_id`, `checked_at`, `method`, `tolerance`, `coverage`, `responsible_party`). | Иначе `CO222` даёт ложное доверие | |

### D. Вариантность

| № | Утверждение | Почему на обсуждении | Решение |
|---|---|---|---|
| D1 | Отказаться от метафор («галактика», «пена») как нормативных сущностей; использовать `VariantScope`, `Candidate`, `Variant`, `Decision`. | Рецензент требует доказуемости | |
| D2 | Кандидаты эфемерны; идентификатор появляется только у сохранённого варианта. | Определяет момент рождения объекта | |
| D3 | Правило «2+1» — UI-сценарий, а не нормативный инвариант ядра. | Слияние трёх реализуемо попарно | |
| D4 | Различать `identity_guid`, `variant_guid`, `lineage`, `persistent_id`. | Снимает противоречие GUID при слиянии | |

### E. Жизненный цикл и итерации

| № | Утверждение | Почему на обсуждении | Решение |
|---|---|---|---|
| E1 | Разделить `Asset lifecycle state` / `Activity participation` / `Information applicability`. | Один `phase` на элементе не работает | |
| E2 | Итерация — граф (`parent_iteration_id`, `scope`, `affected_elements`, `inherited_elements`, `merge_policy`), а не скаляр. | У здания нет одного номера итерации | |

### F. Язык и формат

| № | Утверждение | Почему на обсуждении | Решение |
|---|---|---|---|
| F1 | Формат кода — формальный (ABNF или JSON Schema) с правилами для «неизвестно», «не применимо», диапазона и значений >10. | Иначе это не язык, а строка | |
| F2 | `namespace` не является независимым измерением (производна от фазы и итерации). | Ставит под вопрос ортогональность | |

### G. Управление и статус

| № | Утверждение | Почему на обсуждении | Решение |
|---|---|---|---|
| G1 | Понизить статус до `1.0.0-draft` (Research Draft). | Снимает претензию «ложный Stable» | |
| G2 | Расщепить стандарт на модули со своими инвариантами. | Границы заявлены, но не выдержаны | |
| G3 | Назначить владельца стандарта, процедуру утверждения и conformance testing. | Без этого нет стандарта | |
| G4 | Вехи M1–M3 — отметки событий, а не уровень зрелости. | Позволяет сохранить 1.0 честно | |

## Часть 2. Реестр дыр

Дыры не обсуждаются как тезисы. Каждой назначается владелец и срок. Приоритет: P0 блокирует, P1 важно, P2 уточнение.

### P0 — блокируют

| № | Дыра | Что нужно для закрытия |
|---|---|---|
| Д-01 | Шкала 0–10 без измерительной семантики | Таблица «уровень → признаки → доказательство → тест → роль» по каждому регистру |
| Д-02 | `CO` без эталона и способа подтверждения | Модель доказательства: эталон, дата, метод, допуск, покрытие, ответственный |
| Д-03 | Итерация не определена математически | Графовая модель итераций с политикой слияния ветвей |
| Д-04 | GUID при слиянии вариантов противоречив | Развести identity / variant / lineage / persistent_id |
| Д-05 | Нет матрицы «операция × контекст → Required» | Матрица, которую читает дирижёр напрямую |
| Д-06 | Не определён инвариант совместимости вариантов | Формальное правило: что значит «смешивать нельзя» |
| Д-07 | Отделка и наследование фазы не в модели | Раздел «Отделка как слоистая структура» + правило наследования |

### P1 — важно

| № | Дыра | Что нужно для закрытия |
|---|---|---|
| Д-08 | Комбинаторный взрыв при вариантах по зонам | Pruning, dominance rules, top-k, ограничение глубины |
| Д-09 | Маппинг на СП 333 заявлен как эквивалент | Двусторонняя таблица с описанием потерь; признать фильтром верхнего уровня |
| Д-10 | CDE-статусы дублируют ISO 19650 | Доказать добавку либо удалить и ссылаться на внешнюю политику |
| Д-11 | Формат не разбирается без неявных допущений | ABNF/JSON Schema; проверка парсинга без дефисов |
| Д-12 | Не определена судьба неизменившегося элемента при реконструкции | Правило наследования итерации |
| Д-13 | Не определено, что происходит со слоями при демонтаже зоны | Политика: отделка остаётся, назначение снимается, фаза? |

### P2 — уточнения

| № | Дыра | Что нужно для закрытия |
|---|---|---|
| Д-14 | Коллизии `CO`/`RE`, смысл смешанных состояний (`CO102`) | Таблица допустимых комбинаций |
| Д-15 | Не определены `null`, «не применимо», «не проверяется» | Синтаксис и семантика |
| Д-16 | `TO` смешивает численный допуск и зрелость задания допуска | Развести два понятия |
| Д-17 | Нет политики происхождения атрибутов при слиянии | Правило выбора источника атрибута |
| Д-18 | Нет ответственного за ложную блокировку, override и журнал | Политика override с обоснованием и неизменяемый лог |
| Д-19 | Нет URI/IRI для кодов, нет локализации регистров | Схема идентификации |

## Часть 3. Порядок обсуждения

1. **Статус и вехи** (G1, G4) — 5 мин. Снимает главный конфликт рецензии.
2. **Онтология пространства** (A1–A6) — фундамент, на нём стоит всё.
3. **Отделка и слои** (B1–B6) — закрывает фатальный пункт 2.2.
4. **ЖЦ и итерации** (E1, E2) — закрывает пункты 2.2, 2.3.
5. **Профиль** (C1–C4) — закрывает пункты 2.4–2.6.
6. **Вариантность** (D1–D4) — закрывает пункты 3.1–3.3.
7. **Язык и формат** (F1, F2) — закрывает пункты 2.7–2.9.
8. **Модульность и управление** (G2, G3) — как это всё упаковать.
