# BAIM Naming
## Формальное правило именования файлов · v2.0

**Статус:** рабочий проект
**Основа:** СТО-ТЕХ.И 01-17-01.01 (2017), разд. 4.6 · «Принятая технология ИМ» (4.1)
**Заменяет:** правило именования из СТО 2017 (расширяется, не отменяется)

---

## 1. Назначение и область применения

Правило задаёт машиночитаемый формат имени файла информационной модели и связывает имя
с четырьмя осями идентичности. Применяется к файлам в папках `01_ПРОЕКТЫ` и `00_ОРГПОЛИТИКА`.

Правило расширяет СТО 2017: все сегменты исходного формата сохранены, добавлены три новых
(итерация, статус, представление).

---

## 2. Четыре оси идентичности

Имя файла кодирует четыре независимые оси. Их нельзя смешивать — каждая отвечает
на свой вопрос.

| Ось | Вопрос | Что означает | Аналог | Где живёт |
|---|---|---|---|---|
| **Версия** | какая правка? | промежуточные изменения автора | WIP-цикл | в имени (YY) |
| **Релиз** | какой выпуск? | согласованный выход наружу | revision | в имени (XX) |
| **Итерация** | какая жизнь актива? | исходный объект → реконструкция | fork ЖЦ | в имени (сегмент) |
| **Представление** | какая глубина взгляда? | срез модели под задачу | MVD / LOD | в имени (код) |

**Ключевое разграничение.**
Версия и релиз живут **внутри одной жизни актива**. Итерация — это **новая жизнь**
(реконструкция наследует атрибуты, но начинает свой отсчёт). Представление — **срез**
той же жизни под конкретную задачу.

> **Примечание о терминах.**
> «Представление» — официальный термин (ГОСТ Р 10.0.02-2019: «представление модели, model view»).
> Рабочая метафора — «сумрак» (одна реальность, разная глубина взгляда). В нормативном тексте
> используется только официальный термин.

## 3. Полная структура имени

```
{ЛИЦЕНЗИЯ}-{ШИФР}-{ИТЕРАЦИЯ}-{ФАЗА}-{СОДЕРЖАНИЕ}-({КОММЕНТАРИЙ})-{СТАТУС}-{ПРЕДСТАВЛЕНИЕ}-{РЕЛИЗ}.{ВЕРСИЯ}.{РАСШИРЕНИЕ}
```

Читается слева направо: **кто → что → в какой жизни → на какой стадии → какой раздел →
что именно → для чего годен → как смотреть → какой выпуск и правка**.

---

## 4. Поля

| # | Сегмент | Обяз. | Тип | Источник | Проверка |
|---|---|---|---|---|---|
| 1 | ЛИЦЕНЗИЯ | да | 3 заглавные буквы | реестр договоров (ГИ) | ∈ справочник |
| 2 | ШИФР | да | `NNNN.NN` | реестр договоров (ГИ) | `\d{4}\.\d{2}` |
| 3 | ИТЕРАЦИЯ | да | целое `0–99` | ЖЦ актива | `0` = новый объект |
| 4 | ФАЗА | да | `X-X` | ЖЦ ИМ | ∈ {П-П, А-Э, А-Р} |
| 5 | СОДЕРЖАНИЕ | да | раздел[-подраздел.часть.книга] | СПДС / состав проекта | ∈ справочник |
| 6 | КОММЕНТАРИЙ | нет | текст | СПДС, табл. В.1 | ≤ 32 симв. |
| 7 | СТАТУС | да | `S0–S5` / `A` / `B` | ISO 19650 | **ссылка** |
| 8 | ПРЕДСТАВЛЕНИЕ | да | 1–2 буквы | MVD / СП 333 | ∈ справочник |
| 9 | РЕЛИЗ | да | `NN` | ГИП | ≥ 01 |
| 10 | ВЕРСИЯ | да | `NN` | проектировщик | ≥ 01; `00` = согласовано |
| 11 | РАСШИРЕНИЕ | да | `.ext` | ПО | ∈ {ifc, dwg, doc…} |

## 5. Грамматика (ABNF, RFC 5234)

```abnf
filename   = license "-" objcode "-" iteration "-" phase "-" content
             [ "-(" comment ")" ] "-" status "-" view
             "-" release "." version "." extension

license    = "ТЕХ" / "АКС" / "ИНЖ"
objcode    = 4DIGIT "." 2DIGIT
iteration  = 1*2DIGIT
phase      = ("П" / "А" / "Р") "-" ("П" / "Э" / "Р")
content    = 1*4( ALNUM / "-" / "." )
comment    = 1*( ALNUM / SP / "." / "-" )
status     = "S" %x30-35 / "A" / "B"
view       = 1*2ALPHA
release    = 2DIGIT
version    = 2DIGIT
extension  = 1*5ALPHA
```

> **О кириллице в ABNF.** Классический ABNF (RFC 5234) работает с ASCII; кириллические
> литералы задаются через диапазоны Unicode. Здесь они приведены буквами для читаемости —
> при программной реализации заменяются на `%x04xx`.

## 6. Примеры

**Исходный объект, стадия «Проект», на рассмотрение:**
```
ТЕХ-0747.16-0-П-П-ИОС-1.03.01-(ПЗ)-S3-RV-01.02.ifc
```

**Реконструкция, тот же объект, согласовано:**
```
ТЕХ-0747.16-1-П-П-ИОС-1.03.01-(ПЗ)-A1-DV-00.00.ifc
```

**Сравнение с СТО 2017:**
```
Было:  ТЕХ-0747.16-ИОС-1.03.01-ПЗ-01.02.doc
Стало: ТЕХ-0747.16-0-П-П-ИОС-1.03.01-(ПЗ)-S3-RV-01.02.ifc
```
Добавлено: **итерация** (`0`), **фаза** (`П-П`), **статус** (`S3`), **представление** (`RV`).

## 7. Что мы владеем, а что ссылка

| Сегмент | Владелец | Обоснование |
|---|---|---|
| ЛИЦЕНЗИЯ, ШИФР | **BAIM** | внутренний реестр договоров |
| ИТЕРАЦИЯ | **BAIM** | в ISO 19650 и СТО отсутствует |
| ФАЗА | **BAIM** | из технологии ИМ (4.1) |
| СОДЕРЖАНИЕ, КОММЕНТАРИЙ | ссылка | СПДС / 87 ПП |
| СТАТУС | **ссылка** | ISO 19650 (suitability codes) |
| ПРЕДСТАВЛЕНИЕ | **ссылка** | ГОСТ Р 10.0.02-2019 / СП 333 |
| РЕЛИЗ.ВЕРСИЯ | **BAIM** | ISO 19650 схему нумерации не задаёт |

**Вывод:** владеем осями **итерация**, **релиз.версия** и происхождением. Статус и
представление — заимствуем, не переопределяем.

---

## 8. Правила перехода (релиз и версия)

Наследуются из СТО 2017 без изменений:

1. Релиз начинается с `01`, версия начинается с `01`.
2. В процессе согласования версия увеличивается (`01 → 02 → …`).
3. После согласования всеми участниками **версия → `00`**, релиз не меняется.
4. Следующее изменение: **релиз + 1**, версия → `01`.

---

## 9. Итерация: правило

1. Итерация `0` — исходный объект.
2. Реконструкция порождает **новую итерацию** (`+1`), наследуя атрибуты.
3. Итерация — не число, а узел графа: `iteration_id`, `parent_iteration_id`,
   `scope`, `affected_elements`, `inherited_elements`, `merge_policy`.
4. В имени файла — только номер итерации; полный граф — в метаданных.

---

## 10. Открытые вопросы

1. **Сброс релиз.версия при новой итерации.** Сбрасывать в `01.01` или продолжать?
   Пакет §5.5 говорит «наследует атрибуты» — но это про данные, не про нумерацию.
2. **Статус и представление — в имени или в папке?** При включении в имя строка растёт;
   альтернатива — вынести их на уровень каталога.
3. **Справочник представлений.** Нужен закрытый список кодов (RV, DV, …) либо
   свободное поле с проверкой по bSDD.
