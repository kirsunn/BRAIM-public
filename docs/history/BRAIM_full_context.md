## 1. Что такое BRAIM

**BRAIM** (Building Information Atomic Model) — оркестратор поверх open-source BIM-инструментов. Не пишет движки — управляет ими через шину с Quality Gate.

- **Не авторский инструмент** — не редактирует геометрию
- **Не CDE** — не хранит файлы
- **Оркестратор**: решает, когда ветвить, когда сливать, что проверять, кому отправлять замечания
- Строится на стеке открытых стандартов (IFC, IDS, BCF) и open-source инструментов (IfcOpenShell, Neo4j, git, ifcmerge)

## 2. Глоссарий — перевод между языками

| Термин пользователя | Официальный термин (ISO 19650 / IFC) | Что значит |
|---|---|---|
| атом | информационный контейнер | единица обмена в CDE |
| реестр | информационная модель | набор контейнеров для объекта |
| шина (BuildBus) | CDE + API обмена | транспортная инфраструктура |
| фасет | аспект IDS | грань требования к контейнеру |
| пена | вариантность (variant context) | альтернативные решения в одной итерации |
| метла | Quality Gate | проверка перед слиянием/выпуском |
| вилка | lifecycle_fork (git branch) | ветвление жизненного цикла |
| срез | снапшот итерации (checkpoint) | неизменяемый снимок состояния |
| статус | код состояния (S0–A1) | метаданные CDE, **не имя файла** |
| релиз | revision (P01.02) | выпуск модели для обмена |
| итерация | iteration_snapshot | снимок проектной итерации |
| представление | Model View Definition (MVD) | метаданные, определяют подмножество IFC |

### Правило: имя — для людей, метаданные — для системы

| Слой | Для кого | Что там |
|---|---|---|
| **Имя файла** | человек глазами | идентификатор + релиз + версия |
| **Метаданные CDE** | система | статус, MVD, классификация, автор |
| **Снапшот** | система + человек | контекст: версия стандарта, scope, variants, provenance |

## 3. Пять уровней версионирования

Иерархия сверху вниз — каждый уровень живёт внутри родителя:

```
standard_version   — версия спецификации BRAIM (0.x → 1.0)
  └── iteration_snapshot — снимок проектной итерации (неизменяемый)
        └── release — выпуск модели для обмена (несколько на снапшот)
              └── revision — внутренняя итерация работы над release
                    └── cde_state — состояние в СОД (WIP/SHR/PUB/ARC)
```

| Уровень | В имени файла? | В снапшоте? | В метаданных CDE? | Когда меняется |
|---|---|---|---|---|
| standard_version | нет | да | нет | редко, при несовместимых изменениях спецификации |
| iteration_id | да (`IT04`) | да | нет | каждый checkpoint |
| release | да (`R02`) | да | нет | каждый выпуск наружу |
| revision | да (`.03`) | да | нет | каждая рабочая версия внутри команды |
| cde_state | **нет** | да | **да** | при переходе между состояниями CDE |

### Семантическое версионирование стандарта

| Поле | Когда меняется |
|---|---|
| `MAJOR` (0→1) | несовместимое изменение структуры/смысла |
| `MINOR` (0.1→0.2) | обратно совместимое добавление (в ветке 0.x допускаются ломающие) |
| `PATCH` (0.1.0→0.1.1) | правки формулировок |

### Итерация = счётчик снимков системы

| Событие | Счётчик итераций | Release | Revision |
|---|---|---|---|
| Checkpoint (любой) | +1 | сброс в R00.01 | — |
| Ревизия внутри итерации | та же | +1 к release | +1 |
| Возврат из Hold | +1 (новый снимок) | сброс | сброс |
| Слияние веток | +1 (новый снимок) | сброс | сброс |

**Один механизм для всех случаев:** сделали снимок → счётчик +1, release сбросился.

## 4. Снапшот итерации — структура и принципы

### Структура

```
IterationSnapshot
├── iteration_id          — номер снимка (IT04)
├── project_id            — идентификатор проекта/объекта
├── baim_standard_version — версия спецификации BRAIM (0.1.3)
├── description           — что произошло в этой итерации
├── created_at            — timestamp фиксации
├── scope
│   ├── affected_elements[]  — что изменилось
│   ├── affected_spaces[]    — какие помещения затронуты
│   └── baseline_model_ref    — ссылка на предыдущий снапшот
├── variants[]           — варианты (пена): альтернативные решения
├── decisions[]          — какое решение принято по каждому варианту
├── cde_states[]         — состояния контейнеров (WIP/SHR/PUB/ARC)
├── releases[]           — выпуски модели внутри снапшота
├── profiles[]           — профили (MVD), использованные в итерации
└── provenance[]         — происхождение: git-хэш, автор, ветка, родитель
```

### Три принципа

1. **Снапшот неизменяем** — после фиксации любое изменение = новая итерация
2. **Снапшот хранит контекст** — не только данные, но и версию стандарта, правила, variant context, provenance решений
3. **Снапшот — основа сравнения** — дельта между IT0 и IT1, а не «модель вообще»

## 5. Шесть архитектурных дыр — решения

### Дыра 4: Статус и представление — в имя или в папку?

**Решение:** ни туда, ни туда. Три места, не два:

| Поле | Куда | Почему |
|---|---|---|
| **Статус** (S0–A1) | **метаданные CDE** | меняется часто, по ISO 19650 — это метаданные, не имя |
| **Ревизия** (`P01.02`) | **имя файла** | выпуск, его видно глазами |
| **Представление** (MVD) | **метаданные** | стабильно, свойство контейнера |

Ключевой вывод: смена статуса — **транзакция**, а не переименование. Файл не трогается, ссылки целы.

### Дыра 5: Итерация — сброс или наследование нумерации?

**Решение:** сброс. Итерация = счётчик снимков системы. Каждый checkpoint — новый снимок, счётчик +1, release сбрасывается в R00.01. Наследование не нужно, потому что итерация уже в имени различает файлы.

Модель: пять уровней (см. раздел 3), снапшот неизменяем (см. раздел 4).

### Дыра 6: Класс vs свойство

**Решение:** три уровня, не два.

| Уровень | Что это | Критерий | Пример |
|---|---|---|---|
| **Класс (Entity)** | роль в модели | меняются связи | IfcWall, IfcDoor |
| **Свойство (Pset)** | характеристика | меняется только значение | FireRating = 60 |
| **Классификация** | внешний код | внешний справочник | Uniclass EF_25_10 |

Правило:
```
1. Меняются связи?           → КЛАСС
2. Меняется только значение? → СВОЙСТВО
3. Внешний код системы?      → КЛАССИФИКАЦИЯ (метаданные)
```

### Дыра 7: Граф vs таблицы

**Решение:** не «или», а «оба, но для разного».

```
Граф — источник истины (связи, иерархия, provenance, lifecycle_fork)
Таблицы — проекция графа (агрегация, ведомости, отчёты, Excel)
```

Граф — оригинал. Таблицы — производное, пересобираемое в любой момент. IFC уже устроен как граф (53 типа связей), но реляционные БД с ним борются (joins на many-to-many). Графовые БД (Neo4j) проходят связи напрямую.

### Дыра 8: lifecycle_fork

**Решение:** git-подобное ветвление для BIM. Уже существует — ifcmerge (Rust), Bonsai (BlenderBIM).

- Ветвь создаётся от снапшота — не перезаписывает историю
- Развивается независимо — свои release, revision
- Сливается обратно — создавая **новый снапшот** (+1 к счётчику)
- История — DAG (направленный ациклический граф), не цепочка
- Diff — **графовый**, не текстовый (текстовый diff для IFC бесполезен: та же модель сериализуется в разном порядке строк)

```
IT01 ─── IT02 ─── IT03 ─── IT05 (merge)
              └── IT04 ──┘
```

### Дыра 9: Геометрический валидатор

**Решение:** три уровня проверки, не один.

| Уровень | Что проверяет | Откуда данные |
|---|---|---|
| **Геометрический** | размеры, расстояния, clash | координаты из IFC |
| **Топологический** | связность, смежность, замкнутость | **выводится из геометрии** — в IFC не хранится явно |
| **Функциональный** | соответствие нормам | IDS + bSDD + геометрия + топология |

Пайплайн:
```
BRAIM → шина → геометрический валидатор
                      ├── геометрические проверки
                      ├── топологические проверки (граф)
                      └── функциональные проверки (IDS + bSDD)
                    ↓
              отчёт в BCF → BRAIM → Quality Gate (Go / No-Go / Hold)
                    ↓
              запись в provenance снапшота
```

```

├─────────────────────────────────────────┤
│  4. Валидация (IfcTester / IDS)  готово │
│     проверка по правилам, отчёт BCF     │
├─────────────────────────────────────────┤
│  3. Граф (IfcOpenShell → Neo4j)  готово │

├─────────────────────────────────────────┤
│  2. Версионирование (git + ifcmerge)    │
│     ветвление, слияние, provenance       │
│     ifcmerge — экспериментальное ⚠️      │
├─────────────────────────────────────────┤
│  1. Хранение (git, Neo4j, CDE)   готово │
├─────────────────────────────────────────┤
│  0. Формат (IFC, IDS, BCF, bSDD) готово │
│     открытые стандарты                  │
└─────────────────────────────────────────┘
```

| Слой | Технологии | Лицензия | Статус |
|---|---|---|---|
| 0. Формат | IFC 4.3, IDS 1.0, BCF 3.0, bSDD | открытые | готово |
| 1. Хранение | git, Neo4j, CDE | GPL / GPLv3 | готово |
| 2. Версионирование | git + ifcmerge (Rust) + ifc-commit | open-source | ifcmerge — экспериментальное ⚠️ |
| 3. Граф | IfcOpenShell 0.8.5 → Neo4j (Cypher) | LGPL | готово |
| 4. Валидация | IfcTester (IDS) | LGPL | готово |
| 5. Связь | BCF API 3.0 + OpenCDE API | открытые | готово |
| 6. Авторинг | Bonsai (BlenderBIM) | GPL | готово |
| 7. Веб-просмотр | That Open (web-ifc) / IFClite | MIT / MPL | готово |
| **8. BRAIM** | шина + Quality Gate + снапшоты | 🔨 | **строим** |

### Что строим (нет в open-source)

1. **Оркестратор** — шина, вызывающая движки в правильном порядке с Quality Gate
2. **Геометрический валидатор** — топологические + функциональные проверки
3. **Снапшот-менеджер** — JSON Schema (уже готова, см. раздел 8) + CRUD
4. **Quality Gate** — Go / No-Go / Hold с правилами

### Пайплайн одной строкой

```
IFC → IfcOpenShell → Neo4j → git + ifcmerge → IfcTester (IDS) → BCF → OpenCDE API → BRAIM → Bonsai / That Open
```

## 12. git-IFC — референсные реализации

### Инструменты

| Инструмент | Что делает | Язык | Статус |
|---|---|---|---|
| **ifcgit.py** | UI-панель в Blender: commit, branch, checkout, diff | Python (GitPython) | экспериментальный |
| **ifcmerge** | трёхстороннее слияние IFC-файлов (как `git mergetool`) | Rust | экспериментальный ⚠️ |
| **ifc-commit** | CLI: декомпозирует модель по этажам/дисциплинам, штампует provenance | Python | экспериментальный |
| **Bonsai** (BlenderBIM) | нативная IFC-запись + git UI + visual diff | Python/C | production |

### Как ifcmerge работает

```
ifcmerge base.ifc local_fork.ifc remote_fork.ifc result_merged.ifc
```

Регистрируется как `git mergetool` — git сам его вызывает при конфликтах.

### Три исхода merge = Quality Gate

| Сценарий | Что происходит | BRAIM-аналог |
|---|---|---|
| **Auto-merge** | ветки меняют разные объекты | **Go** |
| **User decision** | оба меняют один объект | **Hold** |
| **Fail** | одна ветка удалила, другая меняет | **No-Go** |

### Графовый diff (Esser et al., 2023)

IFC → labeled property graph → максимальный общий подграф → patch (context, push-out, gluing) → apply.

Три типа узлов:
- **PrimaryNode** — глобальный GUID, стабилен между версиями
- **SecondaryNode** — нет GUID, привязан к primary
- **ConnectionNode** — связи many-to-many

### Pset_GitCommit

ifc-commit вписывает прямо в IFC:
- `CommitHash` — хэш git
- `CommitAuthor` — автор
- `CommitBranch` — ветка
- `CommitMessage` — сообщение

Данные переживают round-trip через Revit/ArchiCAD.

## Механизмы BRAIM (для справки)

| Механизм | Что делает |
|---|---|
| **Транзакция** | атомарное изменение: либо проходит полностью, либо откатывается |
| **Quality Gate** | проверка перед слиянием/выпуском: Go / No-Go / Hold |
| **lifecycle_fork** | создание ветви от снапшота (git branch для BIM) |
| **Checkpoint** | фиксация состояния = новый снапшот, счётчик +1 |
| **Медленная петля** | итерации проекта (недели/месяцы) — снапшоты |
| **Быстрая петля** | ревизии внутри release (дни/часы) — WIP |
