# EIM Maturity Profile

## Статус документа

- Версия: `0.1.0`
- Статус: Draft / концептуальная спецификация
- Дата: 2026-09-25
- Название: `EIM Maturity Profile`
- Назначение: описание зрелости, точности и связности элементов информационной модели на этапах жизненного цикла здания.

> Версия `0.1.0` фиксирует согласованную концепцию и формат. Она ещё не является нормативным стандартом и требует проверки на реальных IFC/Archicad-проектах.

## 1. Назначение

EIM Maturity Profile — машиночитаемая система описания того, насколько информационный элемент или модель готовы к конкретной операции жизненного цикла.

Система должна отвечать на вопросы:

- что известно об объекте;
- насколько определены его геометрия и данные;
- насколько точна геометрия;
- какие внутренние и внешние связи существуют;
- можно ли выполнять расчёты;
- можно ли выпускать документацию;
- готова ли модель к строительству, as-built или эксплуатации.

Система не заменяет IFC, IDS или требования проекта. Она задаёт надстроечный профиль зрелости, который может быть сопоставлен с IFC-сущностями, пользовательскими свойствами, IDS-проверками и правилами EIM Validator.

## 2. Общая структура

Каноническая структура профиля:

```text
G-I-C-A
```

где:

- `G` — Geometry: уровень геометрического представления;
- `I` — Information: уровень информационного наполнения;
- `C` — Conformance: уровень соответствия и согласованности;
- `A` — Accuracy/Maturity: совокупный регистр зрелости геометрии, допуска и связей.

Рекомендуемая человеко- и машиночитаемая запись:

```text
G2-I1-C111-A2[3423;3;343]
```

Полная расшифровка:

```text
G2        геометрический уровень
I1        информационный уровень
C111      уровень соответствия
A2        агрегированный уровень зрелости
3423      GM: размер, форма, местоположение, ориентация
3         TOL: уровень допуска
343       REL: геометрические, логические, информационные связи
```

## 3. Регистр G — Geometry

| Код | Название | Описание |
|---|---|---|
| `G0` | Symbolic | Символ, обозначение или отсутствие объёмного представления |
| `G1` | Approximate volume | Условный объём объекта, системы или сборки |
| `G2` | Material-separated volume | Объём с разделением по материалам или основным слоям |
| `G3` | Constructive geometry | Конструктивное представление с рабочими размерами и составом |
| `G4` | Product geometry | Полное графическое представление изделия или элемента |
| `G5` | Existing-condition geometry | Фактическая геометрия, обследование или облако точек |

## 4. Регистр I — Information

| Код | Название | Описание |
|---|---|---|
| `I0` | Concept information | Основные параметры, ТЭП, назначение и допущения |
| `I1` | Design information | Данные для проектной документации |
| `I2` | Working information | Данные для рабочей документации и строительства |
| `I3` | Fabrication information | Деталировочные данные для изготовления или монтажа |
| `I4` | As-built information | Фактические геометрические и технические данные |
| `I5` | Operational information | Данные оборудования, эксплуатации, обслуживания и ремонтов |

## 5. Регистр C — Conformance

`C` описывает соответствие модели требованиям и связанным данным. Базовые агрегированные значения:

| Код | Название | Описание |
|---|---|---|
| `C000` | No conformance | Соответствие не задано или не проверялось |
| `C001` | Geometric conformance | Геометрия соответствует заданным требованиям |
| `C010` | Internal logical conformance | Внутренние логические связи согласованы |
| `C020` | External logical conformance | Логические связи с внешними моделями или системами согласованы |
| `C100` | Internal informational conformance | Внутренние данные и свойства согласованы |
| `C200` | External informational conformance | Данные согласованы с внешними источниками или моделями |
| `C111` | Design complete | Геометрия, логика и информация соответствуют проектной модели |
| `C222` | Physical complete | Геометрия, логика и информация соответствуют фактическому объекту |

В будущей версии `C` может быть раскрыт в три независимые позиции: геометрическое, логическое и информационное соответствие.

## 6. Регистр A — Accuracy/Maturity

`A` — агрегированный показатель. Он не заменяет подробные параметры, а показывает слабейший уровень внутри регистра.

```text
A = min(GM, TOL, REL)
```

Рекомендуемые уровни:

| Код | Название | Смысл |
|---|---|---|
| `A0` | Undefined | Требования или характеристики отсутствуют |
| `A1` | Symbolic | Символический или условный уровень |
| `A2` | Conceptual | Концептуальный уровень |
| `A3` | Design | Проектный уровень |
| `A4` | Technical | Технический или производственный уровень |
| `A5` | As-built | Фактический уровень по месту |

## 7. Подрегистр GM — Geometric Maturity

`GM` описывает четыре независимых геометрических параметра:

```text
GM = R-F-L-O
```

где:

- `R` — размер / Size;
- `F` — форма / Form;
- `L` — местоположение / Location;
- `O` — ориентация / Orientation.

Каждый параметр имеет уровень от `0` до `5`:

| Уровень | Значение |
|---:|---|
| `0` | Не задано |
| `1` | Символическое или условное представление |
| `2` | Приблизительное представление |
| `3` | Проектное представление |
| `4` | Техническое или производственное представление |
| `5` | Фактическое состояние по месту |

Подробная запись:

```text
GM3423
```

означает:

```text
R3 — размер проектный
F4 — форма технически определена
L2 — местоположение приблизительное
O3 — ориентация проектная
```

Агрегированный уровень:

```text
GM = min(R,F,L,O)
```

Для `GM3423`:

```text
GM = min(3,4,2,3) = 2
```

## 8. Подрегистр TOL — Geometric Tolerance

`TOL` описывает укрупнённый уровень численной геометрической точности.

| Уровень | Смысл |
|---:|---|
| `0` | Допуск не задан |
| `1` | До ±100 мм |
| `2` | До ±50 мм |
| `3` | До ±10 мм |
| `4` | До ±5 мм |
| `5` | Абсолютная или специально заданная точность |

Конкретное значение допуска хранится отдельно:

```json
{
  "tol_level": 3,
  "tolerance_value": 10,
  "tolerance_unit": "mm"
}
```

`TOL3` не обязан означать одинаковый допуск для всех типов элементов. Допуск должен быть определён профилем операции, типа элемента или дисциплины.

## 9. Подрегистр REL — Relationships

`REL` объединяет три типа связей:

```text
REL = G-L-I
```

где:

- первый знак — геометрические связи;
- второй знак — логические связи;
- третий знак — информационные связи.

Каждый компонент имеет уровень от `0` до `5`:

| Уровень | Смысл |
|---:|---|
| `0` | Связь отсутствует |
| `1` | Связь заявлена |
| `2` | Ссылочная связь существует |
| `3` | Связь определена внутри проекта |
| `4` | Связь согласована с внешними данными |
| `5` | Связь подтверждена фактическим объектом или проверенной системой |

Пример:

```text
REL343
```

означает:

```text
G3 — геометрическая связь определена внутри проекта
L4 — логическая связь согласована с внешними данными
I3 — информационная связь определена внутри проекта
```

Агрегированный уровень:

```text
REL = min(G,L,I)
```

Для `REL343`:

```text
REL = min(3,4,3) = 3
```

## 10. Расчёт A

Полный расчёт:

```text
GM = min(R,F,L,O)
REL = min(G,L,I)
A = min(GM,TOL,REL)
```

Пример:

```text
GM = 3423 → GM2
TOL = 3
REL = 343 → REL3
A = min(2,3,3) = A2
```

Полная запись:

```text
G2-I1-C111-A2[3423;3;343]
```

Расшифровка:

```text
G2
I1
C111
A2
  GM3423
  TOL3
  REL343
```

## 11. Требуемый и фактический профили

Для каждого элемента, модели или этапа необходимо хранить отдельные значения:

```json
{
  "required_profile": "G2-I1-C111-A3[3333;3;333]",
  "actual_profile": "G2-I1-C111-A2[3423;3;343]",
  "status": "recheck_required"
}
```

Возможные статусы:

- `unknown` — профиль неизвестен;
- `assumed` — принят как допущение;
- `proposed` — предложен системой;
- `in_progress` — находится в работе;
- `complete` — данные собраны;
- `verified` — профиль подтверждён;
- `outdated` — устарел после изменений;
- `recheck_required` — требуется повторная проверка;
- `rejected` — требования не выполнены.

## 12. Сокращённые и полные формы

Короткая форма:

```text
G2-I1-C111-A2
```

Полная форма:

```text
G2-I1-C111-A2[3423;3;343]
```

Самодокументируемая форма:

```text
G2-I1-C111-A2[GM3423;TOL3;REL343]
```

Для внутреннего API предпочтителен структурированный JSON. Строка используется как display code, идентификатор или компактное представление.

## 14. Использование в процессе

Пример минимальных требований по этапам:

| Операция | Минимальный профиль |
|---|---|
| Идея и анкета | `G1-I0-C000-A1` |
| Генерация планировочного варианта | `G1-I0-C010-A1` |
| Первичные расчёты | `G2-I0-C010-A2` |
| Визуализация и презентация | `G2-I1-C010-A2` |
| Передача в Archicad для доработки | `G2-I1-C100-A2` |
| Проектная документация | `G2-I1-C111-A3` |
| Рабочая документация | `G3-I2-C111-A4` |
| Изготовление или монтаж | `G4-I3-C111-A4` |
| As-built | `G5-I4-C222-A5` |
| Эксплуатация | `G5-I5-C222-A5` |

Значения являются стартовыми профилями и должны уточняться для конкретных дисциплин, типов элементов и нормативных требований.

## 15. Версионность

Использовать Semantic Versioning:

```text
MAJOR.MINOR.PATCH
```

### MAJOR

Изменение структуры, которое нарушает совместимость:

- изменение порядка регистров;
- изменение смысла существующих кодов;
- удаление обязательного поля;
- несовместимый формат строки или JSON.

Пример:

```text
1.0.0 → 2.0.0
```

### MINOR

Обратно совместимое расширение:

- новые значения уровней;
- новые профили стадий;
- новые типы проверок;
- новые необязательные поля.

Пример:

```text
0.1.0 → 0.2.0
```

### PATCH

Исправление ошибок без изменения смысла:

- уточнение описания;
- исправление примера;
- исправление опечатки;
- улучшение формулировки.

Пример:

```text
0.1.0 → 0.1.1
```

## 16. Правила изменения

1. Старые коды не переопределяются без повышения MAJOR.
2. Новые значения добавляются только с описанием диапазона и обратной совместимости.
3. Каждое изменение фиксируется в `CHANGELOG.md`.
4. Все нормативные изменения сопровождаются примерами до/после.
5. Формат JSON является каноническим источником данных.
6. Строковый код является представлением JSON, а не единственным источником истины.
7. Требуемый и фактический профиль никогда не объединяются в одно поле.
8. Неизвестное значение (`null`) не смешивается с нулевым уровнем (`0`).
