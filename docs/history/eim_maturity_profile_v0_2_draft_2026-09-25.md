# EIM Maturity Profile

## Draft v0.2.0

- Статус: Draft / согласованный протокол изменений
- Дата: 2026-09-25
- Проект: BAIM
- Основание: ревью `eim_maturity_profile_v0_1.md`, анализ NZ BIM Handbook v4.1 2023, обсуждение LOa, LOD, координации и field verification.

> Этот документ фиксирует согласованные изменения относительно v0.1.0. Он ещё не является окончательной нормативной спецификацией: шкалы и тестовые примеры требуют отдельной валидации.

## 1. Основные изменения

Вместо старой структуры:

```text
G-I-C-A
```

вводится раскрытая структура:

```text
G-D-C-M-P-R-V
```

Канонический пример:

```text
G2-D1-C111-M3423-P35-R343-V4
```

## 2. Значение регистров

| Регистр | Расшифровка | Назначение |
|---|---|---|
| `G` | Geometry representation | Уровень геометрического представления элемента |
| `D` | Data / Information | Уровень информационного содержания элемента |
| `C` | Conformance | Результат проверки соответствия требованиям |
| `M` | Model geometry maturity | Развитие геометрии модели: размер, форма, местоположение, ориентация |
| `P` | Precision | Точность источника и представления |
| `R` | Relationships | Геометрические, логические и информационные отношения |
| `V` | Verification | Уровень проверки фактического состояния |

## 3. Канонический строковый формат

```text
G<g>-D<d>-C<abc>-M<rfl o>-P<sp>-R<gli>-V<v>
```

Без пробела внутри `M`:

```text
G<g>-D<d>-C<abc>-M<rflo>-P<sp>-R<gli>-V<v>
```

Пример:

```text
G2-D1-C111-M3423-P35-R343-V4
```

Расшифровка:

```text
G2       — геометрическое представление уровня 2
D1       — данные уровня 1
C111     — соответствие: данные, логика, геометрия
M3423    — размер 3, форма 4, местоположение 2, ориентация 3
P35      — точность источника 3, представления 5
R343     — геометрические связи 3, логические 4, информационные 3
V4       — field verification уровня 4
```

## 4. Правила кодовой записи

1. Используются только латинские ASCII-буквы верхнего регистра и цифры.
2. В коротких кодах запрещены `I`, `L`, `O` из-за визуальной путаницы с `1` и `0`.
3. Сегменты разделяются дефисом `-`.
4. Каждый сегмент начинается с буквенного ключа.
5. `A` как отдельный агрегированный регистр исключён из канонического кода.
6. Подробные регистры не дублируются агрегированным значением.
7. Неизвестное значение не кодируется нулём: `0` — известный нулевой уровень, `null` — неизвестно, `not_applicable` — неприменимо.
8. Категориальные значения, если они появятся, записываются как `KEY=VALUE`.

## 5. Регистр G — Geometry representation

| Код | Название | Содержание |
|---:|---|---|
| `G0` | Symbolic | Символ или отсутствие объёмного представления |
| `G1` | Approximate volume | Условный объём объекта, системы или сборки |
| `G2` | Material-separated volume | Объём с разделением по материалам или основным слоям |
| `G3` | Constructive geometry | Конструктивное представление с рабочими размерами и составом |
| `G4` | Product geometry | Полное графическое представление изделия или элемента |
| `G5` | Existing-condition geometry | Геометрия существующего объекта, обследование или облако точек |

`G5` не означает автоматически as-built или field verification.

## 6. Регистр D — Data / Information

| Код | Название | Содержание |
|---:|---|---|
| `D0` | Concept data | Основные параметры, ТЭП, назначение и допущения |
| `D1` | Design data | Данные для проектной документации |
| `D2` | Working data | Данные для рабочей документации и строительства |
| `D3` | Fabrication data | Деталировочные данные для изготовления или монтажа |
| `D4` | As-built data | Фактические геометрические и технические данные |
| `D5` | Operational data | Данные оборудования, эксплуатации, обслуживания и ремонтов |

D-уровень не заменяет конкретный перечень обязательных свойств, который задаётся профилем операции, EIR, BEP, IDS или другим требованием.

## 7. Регистр C — Conformance

Формат:

```text
C[данные][логика][геометрия]
```

| Значение | Содержание |
|---:|---|
| `0` | Соответствие по данному аспекту не подтверждено |
| `1` | Аспект проверен относительно требований внутри проекта |
| `2` | Аспект проверен внутри проекта и относительно указанного внешнего источника |

Примеры:

```text
C001 — геометрия проверена внутри проекта
C010 — логика проверена внутри проекта
C100 — данные проверены внутри проекта
C111 — данные, логика и геометрия проверены внутри проекта
C211 — данные дополнительно проверены по внешнему источнику
C222 — все три аспекта проверены по внешним источникам
```

`C222` не означает автоматически физическое as-built-соответствие. Тип источника, evidence, дату и метод проверки хранить отдельно.

## 8. Регистр M — Model geometry maturity

`M` заменяет прежний `GM` и исключает повторение буквы `G`.

```text
M = [size, form, location, orientation]
```

Позиционная запись:

```text
M3423
```

означает:

```text
size = 3
form = 4
location = 2
orientation = 3
```

Каждая позиция использует уровни `0–5`.

| Уровень | Значение |
|---:|---|
| `0` | Не задано |
| `1` | Символическое или условное представление |
| `2` | Приблизительное представление |
| `3` | Проектное представление |
| `4` | Техническое или производственное представление |
| `5` | Фактическое геометрическое состояние |

`M5` не означает автоматически, что геометрия проверена по месту. За это отвечает `V`.

## 9. Регистр P — Precision

`P` состоит из двух цифр:

```text
P[source][representation]
```

Пример:

```text
P35
```

означает:

```text
точность исходных данных = 3
точность представления в модели = 5
```

Каждый компонент использует уровни `0–5`.

| Уровень | Начальное значение |
|---:|---|
| `0` | Точность не задана |
| `1` | До ±100 мм |
| `2` | До ±50 мм |
| `3` | До ±10 мм |
| `4` | До ±5 мм |
| `5` | Специальный или наиболее строгий допуск, заданный профилем |

Конкретное числовое значение, единица измерения, метод измерения и статистика погрешности хранятся отдельно. `P5` не означает абсолютную точность.

## 10. Регистр R — Relationships

`R` состоит из трёх цифр:

```text
R[geometric][logical][informational]
```

Пример:

```text
R343
```

означает:

```text
geometric = 3
logical = 4
informational = 3
```

Предварительная шкала `0–5`:

| Уровень | Содержание |
|---:|---|
| `0` | Связь отсутствует или явно не задана |
| `1` | Связь заявлена |
| `2` | Адресат или источник связи идентифицирован |
| `3` | Тип и структура связи определены внутри проекта |
| `4` | Связь проверена с учётом внешнего источника или модели |
| `5` | Связь подтверждена как актуальная для конкретной версии/состояния объекта |

Эта шкала требует дальнейшей проверки на тестовых элементах. `R` описывает отношения, но не заменяет результат междисциплинарной координации. Координация должна иметь отдельный результат проверки.

## 11. Регистр V — Verification

`V` описывает уровень проверки фактического состояния. Он вынесен за пределы группы геометрической зрелости, поскольку развитие геометрии и field verification — разные характеристики.

| Код | Название | Содержание |
|---:|---|---|
| `V0` | Not verified | Полевой проверки нет |
| `V1` | Declared | Проверка заявлена, но объективное подтверждение не приложено |
| `V2` | QA verified | Есть QA-документы, акт, чек-лист или исполнительное подтверждение |
| `V3` | Visually verified | Выполнена визуальная проверка соответствия фактическому состоянию |
| `V4` | Measured verified | Выполнена измерительная проверка по месту |
| `V5` | Independently measured | Измерение или контроль выполнены независимой стороной/методом |

Расширенные данные должны содержать метод, источник доказательства, дату, охват и допуск:

```json
{
  "verification": {
    "level": 4,
    "method": "MAB",
    "status": "verified",
    "evidence_id": "survey-014",
    "verified_at": "2026-09-25",
    "tolerance_mm": 3,
    "coverage": "element"
  }
}
```

`V4` не означает, что измерена вся модель. Уровень относится к конкретному элементу, группе или явно указанному охвату.

## 12. Координация

Координация не кодируется автоматически через `R` или `V`.

```json
{
  "coordination": {
    "status": "passed",
    "profile_id": "door-wall-interface-v1",
    "checked_models": ["architecture-04", "structure-03"],
    "tolerance_mm": 10,
    "evidence_id": "coordination-report-014"
  }
}
```

Наличие отношения не равно успешной координации. Соответствие требованиям (`C`) также не равно фактической проверке (`V`).

## 13. Состояния данных

| Значение | Смысл |
|---|---|
| `0` | Известный нулевой уровень или отсутствие свойства |
| `null` | Значение неизвестно или ещё не проверено |
| `not_applicable` | Параметр не применим к объекту или операции |

Неприменимость относится к конкретному требованию или операции, а не всегда к самому элементу.

## 14. Required и actual

Профиль требования и фактический профиль хранятся отдельно:

```json
{
  "required": "G2-D1-C111-M3333-P33-R333-V0",
  "actual": "G2-D1-C111-M3423-P35-R343-V4",
  "status": "recheck_required"
}
```

Сравнение выполняется покомпонентно. Повышенный уровень одной позиции не компенсирует недостаточный уровень другой.

Результат конкретной проверки:

```text
PASS
FAIL
INDETERMINATE
NOT_APPLICABLE
```

## 15. Связь с нормативными подходами

EIM Maturity Profile является собственной системой BAIM и не является кодировкой ISO 19650, ISO 7817-1, российского СП или NZ BIM Handbook.

Он может использоваться совместно с ними:

- `G` и `M` сопоставляются с геометрическими требованиями;
- `D` — с информационным содержанием;
- `P` — с требованиями к точности;
- `R` — с отношениями и зависимостями;
- `C` — с результатами проверки соответствия;
- `V` — с field verification;
- отдельный coordination profile — с координацией моделей.

NZ BIM Handbook v4.1 2023 отделяет уровень разработки элемента от field verification и использует методы NFV, QAV, VAB и MAB. Это подтверждает необходимость отдельного регистра `V` и запрет считать `M5` автоматически as-built.
