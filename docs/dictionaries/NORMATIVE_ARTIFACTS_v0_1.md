# Нормативные артефакты: модель, словарь, конвейер

**Дата:** 2026-10-16 · **Статус:** v0.1 · **Схема:** [`braim-spec/schemas/norm-criterion.json`](../../braim-spec/schemas/norm-criterion.json) (валидирована)

---

## 1. Три сущности — три роли (главное)

| Сущность | Где живёт | Что содержит |
|---|---|---|
| **Свойство (атрибут)** | Словарь: bSDD или локальный bSDD-совместимый **BRAIM Pset** (ADR-015, P0-17) | определение, единица, тип, допустимые значения |
| **Критерий (правило)** | Policy pack: YAML/JSON в **git** (источник истины) | источник + применимость + проверка + провенанс |
| **Связка (маппинг)** | Внутри критерия: `attribute.ifc_binding` + `bsdd_property_ref` | критерий → свойство → IFC-сущность/Pset |

**Критерий не «кладётся в IFC»** — он применяется к IFC-сущности через маппинг на свойство; определение свойства — в словаре. Граф (Norm→Criterion→Calculation→Evidence) — проекция Neo4j, не источник истины.

## 2. Проверка: три вида (по формулировке автора)

| `check.kind` | Смысл | Примеры |
|---|---|---|
| `threshold` | граница: значение/мин/макс/перечень | высота ≥ 2,5 м; REI-предел; `[0.8 м]` дверь |
| `computed` | вычисляемая | `s_naz + s_podz = s_obsh`; инсоляция ≥ 2 ч (расчёт) |
| `presence` | наличие | окно в жилой комнате |
| `script` | детерминированный алгоритм (версионируемый) | эвакуационный путь по графу; пересечения |

## 3. Жизненный цикл критерия

```text
Лингвист (human или LLM, G-5) → needs_source
Распознаватель (код)          → машиночитаемая структура
Верификация (P0-18)           → confirmed (человек, первоисточник, evidence)
Мета-валидация (G-2)          → проверка схемы/дублей/конфликтов/порогов
Human approval                → активация в policy pack
Смена редакции норматива      → superseded + новый критерий (G-1)
```

Статусы `verification`: `needs_source → expert_review → confirmed → superseded`.

## 4. Словарь BRAIM (BRAIM Pset, P0-17)

Наши свойства — в формате **bSDD import model** (ADR-015 DICT-02): собственные определения (`tep.*`, `sp.*`, `geo.*`) с русским+английским, единицами; где существует bSDD-определение — `bsdd_property_ref` на него. Словарь — версияируемый артефакт policy pack (edition+digest). Это наш аналог RusSet_*, но открытый и словарно-совместимый.

## 5. Связь с существующим

- `normbase_seed_v0_1.yaml` (19 критериев из Excel автора) — мигрирует на эту схему (Распознаватель-конвертер, v0.2);
- Attribute Registry v0.1.1 — источник определений атрибутов;
- `validation-result.json` — finding ссылается на `criterion_id`;
- G-1/G-2/G-5/R-05 — встроены в схему полями (`binding_context`, `verification`, `provenance.approved_by`).

## 5.1. Выход конвейера №2: IDS по документу (решение автора 2026-10-16)

Из каждого верифицированного нормативного документа конвейер генерирует **IDS-файл**: `СП_XXXXX → IDS-XXXXXX.ids` (напр. `IDS-SP54_13330_2022.ids`). Референс подхода — Москва: «АГР_Общие требования v9.ids» — это IDS, сделанный из документа требований; мы делаем то же для любых СП/СанПиН.

**Маппинг критерий → IDS 1.0** (проверено прогоном на IDS Москвы):

| norm-criterion | IDS | Ограничение |
|---|---|---|
| `applicability` (Ifc-сущности + условия) | `<specification><applicability>` (entity/property facets) | прямое |
| `check.kind: threshold` (границы свойства) | `<requirement>` (property + xs:restriction) | прямое |
| `check.kind: presence` | `<requirement>` minOccurs ≥ 1 | прямое |
| `check.kind: computed` | **не поддерживается IDS** (cross-element) | BRAIM-воркер |
| `check.kind: script` | **не поддерживается IDS** | BRAIM-воркер |

Сгенерированный IDS проходит мета-валидацию (G-2: XSD + IfcTester smoke-test) и версионируется как артефакт policy pack. Прогон: `ifctester IDS-XXXXXX.ids model.ifc` → результаты сливаются с BRAIM-воркерами в общий `validation-result.json` (findings ссылаются на `criterion_id`).

**Итоговая сборка конвейера:**

```text
PDF → OCR → Лингвист(Ollama) → Распознаватель → norm-criteria (YAML, git)
   → [генератор] → IDS-XXXXXX.ids          (threshold/presence → IfcTester)
   → [генератор] → BRAIM script checks      (computed/script → свои воркеры)
   → [генератор] → bSDD import model        (словарь свойств BRAIM Pset)
   → [генератор] → Cypher-seed              (граф-проекция зависимостей)
```

## 5.2. Словарная политика: водопад сопоставления (решение автора 2026-10-16)

**Вопрос:** что делать со свойствами/критериями, которых нет в bSDD и IFC-сетах? **Ответ: водопад + два слоя словарей, никогда не «или-или».**

### Водопад (для каждого нового свойства из норматива)

| Шаг | Где ищем | При успехе |
|---|---|---|
| 1 | **bSDD** (IFC-сеты, международные) — по смыслу+единице | `match_status: matched_bsdd`, `bsdd_property_ref` на чужой URI (ссылка, не копия) |
| 2 | **Национальные сеты** (RusSet_AGR — шаблон уже в `_library/agr-moscow/lk/`) | `matched_russet` |
| 3 | **КСИ/терминология** (дампы, ГОСТ Р 10.00.00.01-2025) — терминологическая сверка | `matched_ksi` (на уровне терминов) |
| 4 | **Не нашли → создаём в Словаре BRAIM** со статусом `local_original` + пустой `candidate_match` | своё, с полной провенанс-ценью |

У каждого нашего свойства: `match_status` + `candidate_match` (претендент на чужое соответствие) → периодический re-match при релизах bSDD (словари версионируются по датам).

### Два слоя словарей (идея автора)

| Слой | Что | Формат | Назначение |
|---|---|---|---|
| **A. Словарь терминов и определений** | нормативная лексика: «инсоляция», «жилое помещение», «СПП в ГНС»; определение, источник (СП+пункт), синонимы, связанные свойства | наш JSON (bSDD-совместимые поля) | единый язык для Лингвиста и документации; сопоставление понятий между СП и между редакциями (одно понятие в разных СП называется по-разному) |
| **B. Словарь свойств BRAIM Pset** | измеримые величины с единицами и allowed values | **bSDD import model 1:1** (`Classes[]`, `Properties[]`, `UseOwnUri`, `relatedIfcEntityNames`) | проверки + IFC-привязка; загрузка в bSDD как custom dictionary — одной командой (шаблон и Excel2bSDD-конвертер уже есть в экосистеме) |

**Связь слоёв:** термин → свойства (термин «инсоляция» связывает `insolation_hours` и период расчёта). Термины = узлы семантики, свойства = узлы измерений.

### Naming convention

`<domain>.<short_name>`: `tep.*` (ТЭП), `sp.*` (пространства), `geo.*` (геометрия), `fi.*` (пожарные), `acc.*` (МГН), `msk.*` (московские соответствия). **Чужие коды не копируются** — matched-свойство остаётся чужим (URI-ссылка), наш алиас живёт в mapping-файле.

### Референс

`_library/bSDD-reference/` — склонирован official repo (MIT): `Model/Import Model/bsdd-import-model.json` (шаблон), `Excel2bSDD_converter.py` + шаблон (Excel-воркфлоу официально поддержан), примеры custom dictionary. Проверка структуры при генерации — по свежей схеме из репо.
