# Методология: графы зависимостей, составной снапшот, «муравьи-маркеры»

> **Провенанс:** черновик методологии от автора, 2026-10-17 (вечер). Зафиксирован в репо с двумя правками нормализатора (помечены ⚠️ N1, N2). Статус: draft → первый тест на 1–2 помещениях.

## 1. Основная идея: «муравьи-маркеры» на составном снапшоте

Система не делает проверки последовательно. Все модули-ядра запускаются **параллельно на одном и том же снимке** модели (snapshot) и оставляют свои «маркеры проблем».

Аналогия: врачи разных специальностей одновременно осматривают пациента, каждый пишет свой диагноз, координатор собирает единую карту болезней.

**Связь с архитектурой BRAIM:** это ровно наша стадия 4 (EXTRACT/Обогащатель) + параллельные воркеры (см. ROLES.md). Снапшот = наш sealed snapshot (Concept §7) — неизменяемый по построению.

## 2. Структура данных: составной снапшот

```
/snapshots/SNAP-YYYY-MM-DD-XXX/
├── meta.json            # дата, версия, кто создал
├── core_layer.json       # ядро: элементы, типы, статусы (VALID/INVALID)
├── structural_layer.json # конструктор: нагрузки, сечения, материалы
├── estimate_layer.json   # смета: объёмы, расценки, индексы
└── mgn_layer.json        # МГН: проходы, уклоны, габариты
```

**Ключевое правило:** во время диагностики снапшот только читается. Это «фотография больного» на конкретную дату.

> ⚠️ **N1 (правка нормализатора):** в исходном черновике `cascade_impact` содержал `set_status:INVALID, set_volume:0` — **изменение снапшота**, что противоречит его же правилу «снапшот только читается» и нашему Zero Bus (инвариант №1: Raw не перезаписывается). **Решение:** каскады применяются к **обогащённому слою** (enriched/derived overlay), который ссылается на снапшот, но не изменяет его. Diagnosis_map хранит оба: ссылку на снапшот + обогащённый статус. Так формальность сохраняется: «на снапшоте X обогащатель поставил маркер Y по правилу Z».

## 3. Модуль «НОРМЫ» как граф правил

Все зависимости — в декларативный граф `norm_graph.json` (уже есть в `braim_core_skeleton.json`, расширяется DEP-правилами).

- **Зависимости (DEP-xxx):** «Помещение требует 3 замкнутые стены» + каскадные последствия.
- **Нормы (NORM-xxx):** числовые требования с привязкой к СП.

Пример (принят в черновике, с правкой N1):

```json
{
  "rule_id": "DEP-001",
  "name": "Замкнутость помещения стенами",
  "source": "СП 48.13330.2019, п. 5.2",
  "parent": "IfcSpace",
  "child": "IfcWall",
  "relation": "enclosed_by",
  "min_count": 3,
  "validation": "geometry.is_closed == true",
  "cascade_impact": [
    "enriched.set_status:INVALID",
    "enriched.set_volume:0",
    "enriched.set_cost:0",
    "message:Помещение не имеет замкнутого контура стен. Расчёт объёмов и стоимости невозможен."
  ],
  "severity": "CRITICAL"
}
```

**Новый вклад в команду:** DEP-правила выполняет **Обогащатель** (он и есть исполнитель каскадов) — остальные воркеры освобождаются от базовых проверок и работают только по VALID-элементам.

## 4. Цикл работы

1. Создание снапшота из IFC (слои).
2. Обогащатель: зависимости → статусы → каскады (в enriched-слой).
3. Параллельные воркеры («муравьи»): struct / estimate / mgn — по VALID-элементам.
4. Агрегация: `diagnosis_map.json` — единая карта маркеров со ссылками на rule_id и СП.
5. Человек смотрит карту, принимает решение.
6. Изменения → новый снапшот → цикл.

## 5. Вертикаль применения: forensic-аудит (новая вертикаль №6)

Методология прямо пригодна для **судебной/финансовой экспертизы** (проверка заявленных объёмов и стоимости по модели):

- «объём не подтверждён топологией модели» — формальное заключение по DEP-001;
- «смета недостоверна: объём 0 → стоимость 0»;
- артефакты к заключению: `norm_graph.json` (методика), `diagnosis_map.json` (результат на дату), выписки/скриншоты.

> ⚠️ **N2 (правка нормализатора):** конкретные дела и персоналии (ФИО участников) — **приватный контур** (G-6, threat model §3.1). В публичный репозиторий методология попадает в обезличенном виде («forensic use case»), материалы дел — только в `_library`/локально.

**Статус вертикали:** добавлена в Concept v1.1 §1.4 как вертикаль 6 (Phase 2+, после АГР).

## 6. План первого теста (MVP DEP-001)

1. `core/norm_graph.json` в BRAIM-public с DEP-001 + 3–4 базовыми правилами;
2. Тестовый снапшот 1–2 помещений: валидное + с незамкнутым контуром;
3. Обогащатель v0.2: читает DEP-правила, ставит статусы и каскады в enriched-слой;
4. Агрегация `diagnosis_map.json`: у «плохого» помещения объём/стоимость обнулены **в обогащённом слое**, в отчёте — ссылка на правило и СП;
5. Структура папок снапшота — шаблон для будущих.
