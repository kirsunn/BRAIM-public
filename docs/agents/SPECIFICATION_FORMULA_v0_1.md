## Назначение

Этот документ фиксирует доменную формулу формирования технического задания.

Формула является **новой формулировкой, требующей обоснования**, а не переносом существующей формулы из утверждённых источников.

## Формула

```text
Применимые нормативные требования
+ текущее состояние проекта
+ цели и ограничения заказчика / уполномоченной роли
+ ответственные решения утверждающей роли
→ функция формирования ТЗ

→ требования и проверяемые критерии
→ IFC / IDS
→ валидация критериев и модели
→ история изменений
→ аналитика
→ следующая итерация.
```

## Доменная формулировка

Техническое задание формируется на основе:

- применимых нормативных требований;
- текущего состояния проекта;
- целей и ограничений заказчика / уполномоченной роли;
- ответственных решений утверждающей роли.

Функция формирования ТЗ преобразует эти входы в:

- структурированное техническое задание;
- требования;
- проверяемые критерии;
- основания для валидации IFC-модели и IDS-правил;
- фиксацию истории изменений;
- аналитику;
- вход следующей итерации.

## Определения

### Функция формирования ТЗ

```text
Функция формирования ТЗ —
функция, которая преобразует входы
в техническое задание,
требования и проверяемые критерии.
```

В v0.4 «функция формирования ТЗ»
не вводится как отдельная таксономическая сущность.

Вопрос о том, нужна ли для неё
отдельная сущность, модуль или роль,
остаётся открытым.

### Заказчик / уполномоченная роль

```text
Заказчик / уполномоченная роль — роль,
которая задаёт цели и ограничения проекта.
```

В v0.4 термин не отображается
на конкретную роль из ROLES.md.

Соответствие ролям ROLES.md — открытый вопрос.

### Утверждающая роль

```text
Утверждающая роль — роль,
которая подтверждает ответственные решения.
```

В ROLES.md ближайшее соответствие —
роль `Эксперт` (человек, утверждает критерии).

В DESIGN_ITERATION_v0_1.md ближайшее соответствие —
`approved_by: human` в IterationPolicy.

Точное сопоставление — открытый вопрос.

## Статусы сверки

Используются пять исходов:

```text
coincides — смысл совпадает с утверждённым источником.
diverges — смысл расходится; требуется решение.
new — в утверждённых источниках содержания нет.
pending_source_review — Excerpts не предоставлены
или сверка не завершена.
source_not_found — указанный источник не найден
по заявленному пути;
сверка невозможна, пока не уточнены
репозиторий, ветка или путь.
not_covered — источник существует,
но не содержит содержания,
покрывающего данный блок формулы.
```

## Acceptance criteria

Документ может перейти в `accepted`, только если:

1. Формула сформулирована только в доменных терминах.
2. Ни один элемент формулы не зависит от AVGALAXY-метафоры.
3. Для каждого входа и выхода указан источник или статус `new` / `not_covered`.
4. «Функция формирования ТЗ» определена как функция, а не таксономическая сущность.
5. «Заказчик / уполномоченная роль» и «утверждающая роль» имеют явное правило сопоставления с ROLES.md.
6. Все строки сверки имеют статус `coincides`, `diverges`, `new`, `pending_source_review`, `source_not_found` или `not_covered`.
7. ADR-0004 может быть открыт только после перехода документа в `accepted`.

## Что не входит

Этот документ не определяет:

- автоматическую генерацию проектных решений;
- изменение LINKING_MODEL;
- изменение DESIGN_ITERATION;
- изменение ROLES;
- правку архивного BAIM_PROJECT_CONTEXT.md;
- принятие ADR-0004.
