# ADR-0009 — Политика верификации нормативных ссылок

**Статус:** proposed
**Дата:** 2026-10-20
**Контекст:** BRAIM-public, docs/adr/
**Связанные:** ADR-0005, ADR-0006, ADR-0007, ADR-0008, BRAVO v0.4, naming contract v0.3.1, NORMA_CORE_ROADMAP v0.1

## Контекст

Naming contract v0.3.1 зафиксировал принцип: год и обозначение нормативного документа не угадываются.

Драфт `BAIM_PROJECT_CONTEXT.md` нарушил этот принцип: он перечислил СП 333.1325800.2020, СП 404.1325800.2018, СП 480.1325800.2020, СП 301.1325800.2017 и СП 481.1325800.2020 без полей верификации и без источника. СП 548.1325800.2025 — контрольный документ первого среза — в исходном драфте отсутствовал.

Нормативный контур связан с EIM, BAIM Execution Plan, стадиями жизненного цикла, IDS, IFC и валидацией. Непроверенная ссылка может попасть в критерий, правило или проверку, и тогда система будет валидировать проект по несуществующему, устаревшему или неверно понятому документу.

## Проблема

Нет единого правила, которое:

- отделяет проверенные ссылки от непроверенных;
- не даёт непроверенной ссылке попасть в критерий;
- сохраняет историю проверки;
- поддерживает перепроверку при изменении документа.

## Решение

Ввести политику верификации нормативных ссылок и реестр нормативных ссылок как единственный источник сведений о нормативных документах в системе.

### 1. Запись реестра

| Поле | Тип | Обязательное | Смысл |
|---|---|---|---|
| `id` | string | да | стабильный ID, не зависит от обозначения |
| `designation` | string | да | официальное обозначение |
| `year` | integer | да | год |
| `title` | string | да | официальное название |
| `scope` | string | да | область применения |
| `status` | enum | да | статус верификации |
| `source` | string | да | ссылка на источник |
| `verified_by` | string | при verified | кто проверил |
| `verified_at` | date | при verified | когда проверено |
| `evidence` | string | при verified | чем подтверждено |
| `supersedes` | array | нет | какие записи заменяет |
| `superseded_by` | array | нет | чем заменена |
| `notes` | string | нет | комментарии |

### 2. Статусы

```text
verified — обозначение, год, название, область применения
           и актуальность подтверждены источником.

verified_with_caveats — документ подлинный,
           но имеет ограничения области применения,
           редакции или применимости.

needs_verification — запись есть, подтверждения нет.
           Использовать нельзя.

pending_resolution — обозначение или год неполны;
           документ не может быть верифицирован,
           пока не уточнена его идентификация.

superseded — заменена другой записью.

withdrawn — отменена.
```

### 3. Правило допуска

```text
В критериях, правилах, проверках, отчётах и ТЗ
могут использоваться только:

verified
verified_with_caveats
```

Следствия:

- критерий без verified-ссылки не выполняется;
- отчёт, ссылающийся на needs_verification, помечается как неполный;
- ТЗ, построенное на непроверенной ссылке, не утверждается.

### 4. Перепроверка

Любое из событий возвращает ссылку в `needs_verification`:

- изменение обозначения или года;
- публикация новой редакции;
- отзыв документа;
- изменение области применения;
- истечение срока действия.

Перепроверка не удаляет старую запись. Она создаёт новую версию записи через `supersedes` / `superseded_by`.

### 5. Источник правды

Реестр нормативных ссылок размещается в:

```text
BRAIM-public/docs/normative/references
```

Формат хранения — NDJSON, CSV или SQLite — выбирается отдельным решением.

Любая схема, правило или критерий ссылается на `id` записи, а не на строку обозначения.

### 6. Миграция драфта

Все нормативные ссылки в `BAIM_CONTEXT_FRAME_v0.1.md` переводятся в `needs_verification` до подтверждения.

СП 548.1325800.2025 добавляется первым как контрольный документ первого среза.

## Последствия

Положительные:

- непроверенная ссылка не попадает в критерий;
- история проверки сохраняется;
- перепроверка при изменении документа — штатная операция;
- отчётность показывает, на чём основано требование.

Отрицательные:

- до верификации часть критериев не работает;
- нужен процесс верификации;
- нужен реестр и его поддержка.

Нейтральные:

- EIM, IDS и IFC-схемы не меняются;
- меняется только правило допуска ссылок.

## Non-goals

- ADR не выполняет верификацию сам;
- ADR не выбирает, какие документы верифицировать первыми;
- ADR не заменяет юридическую экспертизу;
- ADR не решает, как хранить текст нормативных документов.

## Открытые вопросы

1. Кто уполномочен переводить ссылку в `verified`?
2. Где хранить evidence — в реестре или во внешнем хранилище со ссылкой?
3. Как поступать с документами без официального электронного источника?
4. Нужна ли периодическая перепроверка по расписанию?
